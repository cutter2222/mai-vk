# Цифровой дизайнер презентаций

Сервис генерирует презентацию в стиле загруженного шаблона PPTX по контент-пакету или краткому брифу: разбирает дизайн-систему шаблона, планирует содержание, собирает слайды нативными объектами в трёх вариантах вёрстки, проверяет результат аудитом и экспортирует в PPTX, PDF и HTML.

Проект в разработке. Документация уточняется по этапам; текущее состояние описано ниже.

## Требования

- Python 3.12 и [uv](https://docs.astral.sh/uv/)
- Node.js 22 и [pnpm](https://pnpm.io/) 11
- Docker с compose plugin (для рендеринга и полного запуска)

## Подготовка

```bash
make setup          # uv sync + pnpm install
make gen-contracts  # Pydantic-модели и TypeScript-типы из contracts/schemas
make check          # контракты, ruff, mypy, pytest, eslint, tsc
```

Переменные окружения: скопируйте `config/.env.example` в `.env` в корне и заполните ключ провайдера моделей.

Шаблоны организаторов в репозиторий не входят. Если они есть в `docs/`, `make organizer-data` копирует их в `data/organizers/` с манифестом; тесты с меткой `organizer_data` без этого каталога пропускаются, а при `REQUIRE_ORGANIZER_DATA=1` падают.

## Проверка движка PPTX и рендера

```bash
uv run scripts/inspect_pptx.py data/organizers/*.pptx --json runs/pptx-probe/inspect.json
uv run scripts/probe_pptx.py --templates-dir data/organizers --out runs/pptx-probe --report docs/pptx-capabilities.md
```

`probe_pptx.py` проверяет на каждом шаблоне сохранение без изменений, клонирование образцов, замену текста, нативные таблицу и диаграмму, независимость копий диаграммы и удаление образцов, затем рендерит результаты в PDF и миниатюры (нужен LibreOffice; без него `--skip-render`). Тот же скрипт запускается в образе воркера (`docker compose run --rm worker-generation …`), результаты по машинам собираются в `docs/pptx-capabilities.md`. Открытие файлов в PowerPoint остаётся ручной проверкой по чек-листу из того же документа.

## Анализ шаблона

```bash
uv run -m presentation_designer.cli analyze "data/organizers/VK Tech шаблон.pptx" --out runs/analyze/vktech
# --no-render без LibreOffice, --no-vlm только эвристики, --report сводка в stderr
```

Анализатор (`src/presentation_designer/parsing/template`) читает пакет, разделяет слайды на образцы содержания, инструкции и каталоги иконок, строит палитру, шрифты и шкалу кеглей с областью действия, находит постоянные элементы и ресурсы, превращает образцы в композиционные паттерны со слотами (ёмкость по метрикам шрифтов рендерера) и правилами из текста шаблона, объединяет образцы одной сигнатуры в группы взаимозаменяемых (`group_id`) и определяет тон фона каждого образца (`tone`: заливка слайда, закрывающая картинка, фон макета, мастера или тема) и стиль `style_key` «тон|семейство макета|plain»; миниатюры — LibreOffice → PDF → PNG под слотом рендера, роли образцов уточняет VLM по представителям групп. Тот же анализ выполняет воркер при `POST /api/templates`; результаты на четырёх шаблонах — [docs/template-analysis.md](docs/template-analysis.md).

## Импорт содержания и смысловой план

```bash
uv run -m presentation_designer.cli import examples/content/ --out runs/import/
# --no-model без уточнения контекста фактов моделью, --no-cache перечитать файлы, --report сводка
uv run -m presentation_designer.cli story runs/import/package.json --out runs/import/story.json
# --settings settings.json явные настройки запроса (language, slide_count, seed), --no-model черновик без модели
```

Импортёр (`src/presentation_designer/parsing/content`) разбирает docx, xlsx и csv, pdf с текстовым слоем, markdown и txt, pptx как материал (текст слайдов и заметок, таблицы, данные диаграмм, картинки) и изображения в общую модель блоков, кэширует разбор каждого файла по sha256 и версии парсера (`data/import-cache`: смена брифа или удаление одного материала не перечитывает остальные), собирает реестр фактов с контекстом (показатель, период, субъект, единица, сравнение, исходный фрагмент или ячейка), производные показатели с формулой и наборы данных с типами колонок; неоднозначный контекст фактов уточняет модель (скилл `content_importer`) со ссылкой на фрагмент, значения она не переписывает. Бриф из сообщения чата извлекает скилл `brief_extractor` (без рассуждения, тайм-аут `timeouts.brief_s`), при недоступности модели — те же правила, что в интерфейсе, с `source: heuristic`. Смысловой план StoryPlan (`src/presentation_designer/generation/story.py`, скилл `story_planner`) строится один раз на содержание и эффективный бриф: тезисы ссылаются на блоки, факты, наборы данных и изображения, покрытие обязательных фактов и пунктов брифа проверяет код; кэш плана — по `content_hash`, а не по идентификаторам заданий. Собственный контент-пакет для проб — `examples/content/`.

## Планы трёх вариантов

```bash
uv run -m presentation_designer.cli plan runs/import/story.json runs/analyze/profile.json \
    --content runs/import/package.json --variants compact,balanced,detailed --out runs/plan/
# --no-model детерминированный черновик, --no-cache без кэша готовых планов, --report сводка
```

Планировщик (`src/presentation_designer/generation/variants.py`, скилл `variant_planner`) строит из общего StoryPlan и профиля шаблона по одному SlidePlan на вариант оси плотности: титульный, разделители, оглавление и финальный слайд подбираются кодом из всего пула роли — внутри колоды одним стилем (`style_key`), а у compact/balanced/detailed разными (`plan.style_policy: per_variant`; `first` — первый паттерн пула у всех), титул и финал в тон разделителя; серии одинаковых композиций разбавляются сначала братьями по группе образцов, затем другими кандидатами; содержательные тезисы делятся на пакеты по разделам, для каждого тезиса код отбирает кандидатов-композиций по подаче, вместимости и поддерживаемой визуализации (`matching.py`: таблица только при слоте таблицы, диаграмма — при слоте диаграммы или картинке диаграммы в образце), а модель получает пакет тезисов с фактами, короткий список композиций с ёмкостью и правила варианта и выбирает группировку и формулировки, ссылаясь на факты через `{fact:<id>}`; пакеты идут параллельно под общим deadline, негодный пакет повторяется с подсказкой отдельно. Слоты, подстановку фактов и измерение по файлам шрифтов рендерера выполняет код (`capacity.py`): при переполнении — более вместительная композиция, кегль из шкалы шаблона, сокращение без потери фактов, разделение слайда в пределах диапазона; невозможность разместить обязательное при точном числе слайдов — структурированная ошибка, а не тихая потеря. Планы проверяются валидаторами связей (слоты, факты, число слайдов, покрытие тезисов), сравниваются по последовательности композиций и визуализации — содержательных слайдов отдельно, чтобы разные разделители не маскировали одинаковое содержание (пары без различий записываются предупреждением `variants_indistinct`); разнообразие колоды измеряет `scripts/deck_diversity.py` по планам и ComposedDeck (доля самой частой композиции, серии, стили разделителей, иконки из плана, расстояние между вариантами; строки «до/после» в [docs/evaluation.md](docs/evaluation.md)) и кэшируются в `data/plan-cache` по StoryPlan, структуре и ёмкости паттернов, метрикам шрифтов, настройкам и версиям скилла.

## Вёрстка PPTX

```bash
uv run -m presentation_designer.cli compose runs/plan/balanced.json --profile runs/analyze/profile.json \
    --template tests/fixtures/pptx/mini_template.pptx --content runs/import/package.json --out runs/compose/balanced/
# --prune-layouts убрать неиспользуемые макеты, --pdf ещё и PDF через LibreOffice, --report отчёт
```

Композер (`src/presentation_designer/layout/compose.py`) берёт исходный PPTX как основу: для каждого слайда плана клонирует образец паттерна с графом связей (макет общий, картинки разделяются, диаграммы с книгами данных копируются), заполняет слоты по `element_ref` — текст с сохранением оформления абзацев и фрагментов и явным кеглем из `fit.size_pt`, факты значениями как в источнике, списки абзацами по маркированному абзацу образца, таблицы по строкам-шаблонам таблицы образца, нативные диаграммы (в слоте chart — данные в диаграмму образца, вместо картинки диаграммы — новая на её месте; так же и с диаграммой, нарисованной руками: ряд столбиков из картинок распознаётся анализатором целиком — `parsing/template/drawn_charts.py` — становится одним слотом chart, а его части перечислены в `chart_parts` паттерна и убираются, когда диаграмма построена), схемы из фигур, картинки пакета с crop, иконки шаблона с перекраской масок; незаполненные карточки убираются по `removable_object_ids` вместе с пустыми рамками, статика и логотипы остаются, крошечные слоты (номера шагов) сохраняют текст образца. Образцы удаляются, номера слайдов пересчитываются, пакет проверяется (`layout/integrity.py`), по сохранённому файлу строится ComposedDeck (`layout/composed.py`: объекты, геометрия, вычисленные стили, ресурсы, связь со слотами и блоками, `content_source` у каждого объекта). Требование сохранности профиля: `template_hash` профиля должен совпадать с файлом шаблона.

## Правка слайда по запросу

```bash
uv run -m presentation_designer.cli edit-slide runs/plan/balanced.json --story runs/import/story.json \
    --profile runs/analyze/profile.json --content runs/import/package.json \
    --slide 5 --instruction "сделай заголовок короче и вынеси 40 % в показатель" --out runs/edit/
# затем compose по runs/edit/plan.json; --report сводка (композиция до/после, переполнения, отказ)
```

В редакторе выбранный в ленте слайд становится адресатом чата: над полем ввода появляется чип «Слайд 5 · Сбалансированный · r1» (крестик снимает адресацию), а просьба «сделай заголовок короче», «добавь пункт про сроки», «покажи это диаграммой», «замени карточки списком» уходит в `POST /api/generations/{job}/variants/{variant}/edits` и создаёт новую ревизию выбранного варианта, как исправление по находкам аудита. Слой правки (`src/presentation_designer/generation/edit.py`, скилл `slide_editor`) даёт модели инструкцию, текущий слайд с композицией и ёмкостью, соседей, тезисы слайда, факты и наборы данных пакета и короткий список композиций (кандидаты по тезисам плюс пул подачи, которую просят); ответ в формате планировщика для одного слайда проходит тот же путь, что и при генерации: сборка слотов, измерение ёмкости с повтором по подсказке, замена слайда в плане с прежними `slide_id` и `order`, `revision_note`, проверка связей, затем compose → export → audit только новой ревизии. Цифры не выдумываются: факты только ссылками `{fact:<id>}`; просьба, для которой нет данных или которая касается не этого слайда (добавить или переставить слайды), отклоняется с причиной, ревизия не создаётся. Карточка в чате показывает ход, «до/после» и что изменено; панель ревизий и «Как собран слайд» хранят историю правок. Перестановка, добавление и удаление слайдов и правка сразу во всех вариантах не реализованы.

## Визуальный редактор слайдов

```bash
uv run -m presentation_designer.cli patch-slides runs/compose/balanced/plan.json --patch runs/patch/patch.json \
    --profile runs/analyze/profile.json --content runs/import/package.json \
    --deck runs/compose/balanced/composed.json --out runs/patch/
# затем compose по runs/patch/plan.json (для правок с источником file — с --uploads data/uploads)
```

Ручные правки объектов готового слайда: текст, кегль, начертание, цвет и выравнивание, положение и размер (в том числе внутри групп), замена картинки или иконки из ресурсов шаблона, материалов пакета или своего файла с перекраской монохромных иконок, удаление объекта (клавиша Delete или кнопка в панели), своя надпись на слайде (кнопка «Текст»), фон слайда (цвет, картинка, «как в макете») и перестановка слайдов. Правки хранятся в плане варианта как `slides[].overrides` и применяются композером после заполнения слота (`src/presentation_designer/layout/overrides.py`), поэтому ревизия воспроизводится из плана, а правка из чата сбрасывает ручные правки только у переделанного слайда (`overrides_dropped`). Документ `slide_patch` (`contracts/schemas/slide_patch.schema.json`) уходит в `POST /api/generations/{job}/variants/{variant}/patches` и создаёт новую ревизию без модели тем же путём, что правка из чата; `edits[]` результата помечает такие правки `origin: editor`. Адрес объекта — `object_id` из ComposedDeck базовой ревизии с охраной `source_object_id`/`slot_id`: несовпадение — правка отброшена с предупреждением. Своя надпись (`op: add_text`) адресуется придуманным редактором `usr_…`: объекта с таким адресом в базовой ревизии нет, номер готовой фигуры выводится из него детерминированно, поэтому пересборка ревизии из плана повторяема, а правки текста и положения той же надписи в том же патче находят её по придуманному адресу. Значения вне токенов шаблона применяются с предупреждением `override_off_template`, текст, не помещающийся после правки, — `override_overflow`. Медиа колоды лежит рядом с ревизией (`media/`, `assets[].artifact`), ресурсы шаблона отдаёт `GET /api/templates/{id}/media/{asset_id}`, а для подложки холста анализ рендерит пустой слайд каждого макета (`previews/layout-<id>.png`).

## Модели

```bash
make llm-smoke          # один реальный вызов модели: ключ и адрес из .env
make llm-probe          # зонд провайдера с отчётом в docs/llm-capabilities.md
make llm-limiter-check  # лимитер из нескольких процессов против Valkey
```

Все вызовы моделей идут через пакет `src/presentation_designer/llm`: клиент на openai SDK с `base_url` провайдера, роли `llm`/`vlm` из `config/models.yaml`, общий для всех воркеров лимитер одновременности, RPM и TPM в Valkey, свои повторы (429, сеть, 5xx, негодный ответ) в пределах deadline, кэш ответов в `data/llm-cache`, записанные ответы для тестов (`tests/fixtures/llm`, режимы `record`/`replay`) и учёт usage по этапам. Скиллы — `skills/<name>/skill.yaml` с версионируемыми промптами; версия промпта входит в ключ кэша и в результат. Возможности endpoint (model ID, JSON-схема, изображения, streaming, рассуждение, одновременность) измеряет зонд, результат — [docs/llm-capabilities.md](docs/llm-capabilities.md); до зонда слои конвейера работают в режиме заглушек.

## Сервер и интерфейс

```bash
make api            # локальный API без Docker: задачи выполняются сразу, Valkey не нужен
make dev-real       # интерфейс на http://localhost:3000, /api проксируется на локальный API
make dev            # интерфейс в режиме заглушек: весь сценарий в браузере без backend
make e2e            # сквозные тесты в Chromium, Firefox и WebKit против статического экспорта
make build          # статический экспорт для сервера (рабочий режим, API того же origin)
```

Сервер — FastAPI (`src/presentation_designer/api`), состояние в SQLite, очередь RQ поверх Valkey: воркер анализа и исправлений и три воркера генерации. Слои конвейера подключаются по этапам, а `execution_mode` в результате и `/api/health` показывает, какие настоящие: анализ шаблона, импорт, бриф, смысловой план, планы вариантов, вёрстка и экспорт (PDF и миниатюры собранного PPTX через LibreOffice, HTML разметкой объектов слайда из ComposedDeck) уже настоящие, детерминированная часть аудита (24 проверки Приложения 1 по ComposedDeck) тоже настоящая, контекстная часть и исправления — заглушки с отметкой `stub`, которые возвращают документы из примеров контрактов. Без LibreOffice на машине экспорт тоже остаётся заглушкой. Режим API интерфейса фиксируется при сборке переменной `NEXT_PUBLIC_API_MODE` (`real` по умолчанию, `mock` для заглушек в браузере): публичные переменные Next.js встраиваются в bundle. Экраны: `/` — сетка проектов (каждый проект — одна презентация с миниатюрой и состоянием); `/project?id=…` — редактор проекта: слева чат, в который пользователь бросает PPTX-шаблон и материалы и описывает задачу одной фразой (каждый шаг конвейера — карточка: шаблон, материалы, понятый бриф, ход задания, аудит, правка слайда), рядом вкладка «Файлы проекта»; справа предпросмотр (до генерации — выбранный шаблон одной миниатюрой со ссылкой на его разбор, после — слайды вариантов с панелью аудита); `/templates` — библиотека шаблонов: сетка карточек, а внутри шаблона (`/templates?id=…`) всё, что извлёк анализ: композиции со слотами поверх образца, классификация слайдов файла, палитра, шрифты и шкала кеглей, постоянные элементы, макеты и ресурсы, дайджест для модели и JSON профиля; шаблон можно удалить из библиотеки. Прежний адрес `/workspace?job=…` перенаправляет в проект. Проекты, файлы, бриф, настройки и лента чата хранятся на сервере: проект открывается по ссылке из любого браузера. Бриф из свободного текста извлекает `POST /api/brief`: пока детерминированная эвристика (`source: heuristic`), модель подключается на этапе импорта содержания.

## Отладка

```bash
uv run python tools/job_doctor.py                  # сверка артефактов всех заданий между собой
uv run python tools/job_doctor.py job_ab12… -v     # одно задание, построчная сверка текста слайдов
uv run python tools/ui_doctor.py prj_ab12…         # интерфейс вживую: тот ли слайд и те ли рамки
```

Слайд доходит до пользователя тремя путями: миниатюра и PDF от рендерера, `composed.json` для
редактора и рамок аудита, `deck.pptx` для скачивания. Если они разойдутся, интерфейс покажет
один слайд, а править и проверять будет другой. `job_doctor` сверяет состав файлов, число
слайдов, порядок (по тексту слайдов из pptx и текстового слоя PDF), нумерацию в описании,
ссылки находок на слайды и объекты и рамки в пределах холста. `ui_doctor` водит настоящий
Chrome по ленте миниатюр и сверяет нарисованные рамки с `audit.json`, включая перестановку
слайдов в черновике редактора. Оба возвращают код 1 при расхождении и годятся для CI.

## Развёртывание

```bash
make up             # весь стек в Docker Compose на этой машине: http://localhost:8080
make down           # остановить локальный стек
make test-server    # интеграционные тесты API и сквозные тесты интерфейса против сервера (или локального стека)
./deploy/install.sh --target server   # Docker и каталоги на сервере из deploy/server.env
./deploy/deploy.sh --target server    # выкладка: образы с тегом выпуска, миграция, ожидание готовности
./deploy/deploy.sh --target server --rollback   # откат на предыдущий выпуск одной командой
./deploy/backup.sh --target server    # резервная копия: база снимком, загрузки, артефакты, Valkey
./deploy/restore.sh --target server --verify-only   # проверка копии в отдельном каталоге; без флага — восстановление
```

Сервер Ubuntu, Docker Compose: вход Caddy с автоматическим TLS (h1/h2), статический интерфейс, API, воркеры (образ с LibreOffice и шрифтами), Valkey; на сервере к базовому compose добавляется `docker/compose.prod.yaml` с пределами памяти по замерам, ротацией логов и слотами рендера. Сборка мусора хранилища и артефактов идёт периодической задачей воркера анализа по срокам из `config/app.yaml`. Адрес и SSH-доступ задаются в `deploy/server.env` по образцу `deploy/server.env.example` и в Git не попадают. Подробности: [docs/deploy.md](docs/deploy.md), замеры запуска — [docs/evaluation.md](docs/evaluation.md).

## Ограничения

- Настоящие слои: анализ шаблона, импорт содержания, извлечение брифа, общий смысловой план, планы вариантов, вёрстка PPTX и экспорт (PDF, миниатюры, HTML). Аудит пока заглушка — результат помечен `execution_mode: mixed` и не выдаётся за генерацию. Без LibreOffice на машине экспорт тоже остаётся заглушкой.
- Схемы строятся из нативных фигур и соединителей, а не как объект SmartArt; внешние библиотеки иконок (`icon.query`) и генерация изображений (`image.generate`) не подключены — слот сохраняет иконку образца с предупреждением.
- Шрифты рендерера: в образе воркера есть Play, Montserrat, Poppins, шрифты Microsoft «Core fonts» (Arial, Times New Roman, Courier New, Verdana, Georgia…), Liberation, Carlito, Caladea, Noto, DejaVu; проприетарные шрифты без лицензии на распространение (Consolas, Segoe UI, VK Sans) заменяются с предупреждением `font_substituted` в профиле, метрически совместимые клоны подменой не считаются (`font_metric_equivalent`). В PPTX всегда остаётся исходное имя шрифта — PowerPoint показывает свой.
- Правка по запросу меняет один слайд одного варианта и требует модели (в заглушках — детерминированная подмена заголовка); добавление и удаление слайдов из чата не поддерживаются, перестановка — только из редактора (`order` в патче).
- Визуальный редактор добавляет только свою надпись (фигур, картинок и таблиц не создаёт), удаляет любой объект слайда и снимает знак шаблона со всей колоды (`template_logo: drop` в плане и в `slide_patch`: логотип шаблона лежит на макетах, а не на слайде, поэтому правкой объекта его не убрать — шаблон другого подразделения перестаёт быть непригодным); фон-картинка образца (объект с ролью `background`) заменяется, но не убирается; содержимое таблиц, диаграмм и схем не правится; поворот не поддерживается; правки адресуют текущую ревизию собранного варианта.
- Стиль титула, разделителей и финала внутри колоды единый, чередование стилей внутри колоды не делается; иконки в слотах пока берутся из образца (подбор по смыслу из ресурсов шаблона — этап 15), фото и фоны макетов не заменяются (этап 16).
- Неиспользуемые макеты по умолчанию остаются в файле (`layout.prune_unused_layouts: false`): так в PowerPoint у пользователя доступен полный набор макетов шаблона; включение уменьшает файл VK Education с 17,7 до 0,6 МБ.
- Один арендатор без авторизации: все проекты видны каждому, кто открыл адрес сервиса.
- PDF без текстового слоя (сканы) не распознаются: файл помечается предупреждением, в пакет попадает только изображение страницы.
