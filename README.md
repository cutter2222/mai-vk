# Цифровой дизайнер презентаций

Сервис генерирует презентацию в стиле загруженного шаблона PPTX по контент-пакету или краткому брифу: разбирает дизайн-систему шаблона, планирует содержание, собирает слайды нативными объектами в трёх вариантах вёрстки, проверяет результат аудитом и экспортирует в PPTX, PDF и HTML.

Проект в разработке. Состояние на 21 сентября 2026: ONLYOFFICE используется для просмотра и редактирования PPTX и серверного рендера; в проект подключён контекстный чат. Генерация и аудит работают, но качество презентаций ещё требует проверки — успешное завершение задания не означает отсутствие дефектов.

## Как работать с проектом

1. Создайте проект и выберите шаблон из библиотеки или загрузите PPTX в первом сообщении чата. До генерации исходный шаблон открывается в ONLYOFFICE **только для просмотра**.
2. Опишите задачу и добавьте материалы. Бриф, настройки, файлы и история разговора сохраняются на сервере.
3. Запустите генерацию. Первый опубликованный PPTX можно открыть, пока остальные варианты и аудит выполняются в фоне. Это публикация готового варианта, **не потоковое добавление отдельных слайдов**.
4. Задавайте вопросы в чате: ассистент получает с сервера контекст шаблона, материалов, брифа, настроек, статуса генерации и аудита выбранного варианта. Подсказки под ответом только подставляют текст в поле ввода и не запускают действия сами.
5. Редактируйте презентацию в ONLYOFFICE. Для ИИ-правки текста открытого PPTX используйте явную команду `/edit инструкция`; обычный вопрос не меняет документ. При `/edit` интерфейс запрашивает закрытие редактора и ждёт подтверждения сохранения сервером; при ошибке правка не запускается. Для смены варианта завершите редактирование и явно откройте выбранную версию.
6. Скачайте PPTX, PDF или HTML через меню в шапке. Экспорт использует выбранную сохранённую офисную ревизию; перед скачиванием последних ручных правок сохраните документ. HTML офисной версии — автономная страница с изображениями слайдов, а не редактируемая вёрстка.

Текст можно надиктовать: кнопка микрофона слева от «Отправить» включает запись, каждая законченная фраза распознаётся на сервере (GigaAM, русский язык, со знаками препинания) и дописывается в поле, пока вы говорите. После выключения текст остаётся в поле — поправьте и отправьте как обычно. Модель работает в отдельном сервисе стека `asr`; без её весов кнопки нет. Подробности — [docs/speech.md](docs/speech.md).

Готовую презентацию можно открыть как есть: бросьте PPTX в чат и выберите «Открыть как презентацию». Копия файла публикуется прямо в ответе на запрос, и ONLYOFFICE показывает слайды, как только откроет файл; в чате — «Презентация открыта за N с». Разбор идёт в фоне и ничему не мешает: подписи пустых плейсхолдеров и диаграммы-картинки становятся новой ревизией (редактор переключается на неё сам, если вы ещё ничего не правили, иначе предлагает её баннером), затем разбор шаблона, план и проверки. Править руками и через `/edit` можно сразу; просьба к слайду по номеру («на слайде 3 сократи текст») ждёт разбора, и чат говорит, через сколько её применит. Проверка слайдов моделью при открытии выключена — её можно запустить из подробностей задания.

Открытая офисная сессия закреплена за своим артефактом, пока вы её правите: фоновое завершение генерации не пересоздаёт iframe и не подменяет документ с правками. Ручные правки остаются в офисной копии, исходник генерации сохраняется отдельно; в другую сборку эти правки автоматически не переносятся.

## Требования

- Python 3.12 и [uv](https://docs.astral.sh/uv/)
- Node.js 22 и [pnpm](https://pnpm.io/) 11
- Docker с compose plugin (для рендеринга и полного запуска)

## Подготовка

```bash
make setup          # uv sync + pnpm install
make gen-contracts  # Pydantic-модели и TypeScript-типы из contracts/schemas
make check          # контракты, ruff, mypy, pytest, eslint, tsc
```

Переменные окружения: скопируйте `config/.env.example` в `.env` в корне и заполните ключ провайдера моделей.

Шаблоны организаторов в репозиторий не входят. Если они есть в `docs/`, `make organizer-data` копирует их в `data/organizers/` с манифестом; тесты с меткой `organizer_data` без этого каталога пропускаются, а при `REQUIRE_ORGANIZER_DATA=1` падают.

## Проверка движка PPTX и рендера

```bash
uv run scripts/inspect_pptx.py data/organizers/*.pptx --json runs/pptx-probe/inspect.json
uv run scripts/probe_pptx.py --templates-dir data/organizers --out runs/pptx-probe --report docs/pptx-capabilities.md
```

`probe_pptx.py` проверяет на каждом шаблоне сохранение без изменений, клонирование образцов, замену текста, нативные таблицу и диаграмму, независимость копий диаграммы и удаление образцов, затем рендерит результаты в PDF и миниатюры (нужен ONLYOFFICE; без него `--skip-render`). Тот же скрипт запускается в образе воркера (`docker compose run --rm worker-generation …`), результаты по машинам собираются в `docs/pptx-capabilities.md`. Открытие файлов в PowerPoint остаётся ручной проверкой по чек-листу из того же документа.

## Анализ шаблона

```bash
uv run -m presentation_designer.cli analyze "data/organizers/VK Tech шаблон.pptx" --out runs/analyze/vktech
# --no-render без ONLYOFFICE, --no-vlm только эвристики, --report сводка в stderr
```

Анализатор (`src/presentation_designer/parsing/template`) читает пакет, разделяет слайды на образцы содержания, инструкции и каталоги иконок, строит палитру, шрифты и шкалу кеглей с областью действия, находит постоянные элементы и ресурсы, превращает образцы в композиционные паттерны со слотами (ёмкость по метрикам шрифтов рендерера) и правилами из текста шаблона, объединяет образцы одной сигнатуры в группы взаимозаменяемых (`group_id`) и определяет тон фона каждого образца (`tone`: заливка слайда, закрывающая картинка, фон макета, мастера или тема) и стиль `style_key` «тон|семейство макета|plain»; миниатюры — ONLYOFFICE → PDF → PNG под слотом рендера, роли образцов уточняет VLM по представителям групп. Тот же анализ выполняет воркер при `POST /api/templates`; результаты на четырёх шаблонах — [docs/template-analysis.md](docs/template-analysis.md).

## Импорт содержания и смысловой план

```bash
uv run -m presentation_designer.cli import examples/content/ --out runs/import/
# --no-model без уточнения контекста фактов моделью, --no-cache перечитать файлы, --report сводка
uv run -m presentation_designer.cli story runs/import/package.json --out runs/import/story.json
# --settings settings.json явные настройки запроса (language, slide_count, seed), --no-model черновик без модели
```

Импортёр (`src/presentation_designer/parsing/content`) разбирает docx, xlsx и csv, pdf с текстовым слоем, markdown и txt, pptx как материал (текст слайдов и заметок, таблицы, данные диаграмм, картинки) и изображения в общую модель блоков, кэширует разбор каждого файла по sha256 и версии парсера (`data/import-cache`: смена брифа или удаление одного материала не перечитывает остальные), собирает реестр фактов с контекстом (показатель, период, субъект, единица, сравнение, исходный фрагмент или ячейка), производные показатели с формулой и наборы данных с типами колонок; неоднозначный контекст фактов уточняет модель (скилл `content_importer`) со ссылкой на фрагмент, значения она не переписывает. Бриф из сообщения чата извлекает скилл `brief_extractor` (без рассуждения, тайм-аут `timeouts.brief_s`), при недоступности модели — те же правила, что в интерфейсе, с `source: heuristic`. Смысловой план StoryPlan (`src/presentation_designer/generation/story.py`, скилл `story_planner`) строится один раз на содержание и эффективный бриф: тезисы ссылаются на блоки, факты, наборы данных и изображения, покрытие обязательных фактов и пунктов брифа проверяет код; кэш плана — по `content_hash`, а не по идентификаторам заданий. Собственный контент-пакет для проб — `examples/content/`.

## Планы трёх вариантов

```bash
uv run -m presentation_designer.cli plan runs/import/story.json runs/analyze/profile.json \
    --content runs/import/package.json --variants compact,balanced,detailed --out runs/plan/
# --no-model детерминированный черновик, --no-cache без кэша готовых планов, --report сводка
```

Планировщик (`src/presentation_designer/generation/variants.py`, скилл `variant_planner`) строит из общего StoryPlan и профиля шаблона по одному SlidePlan на вариант оси плотности: титульный, разделители, оглавление и финальный слайд подбираются кодом из всего пула роли — внутри колоды одним стилем (`style_key`), а у compact/balanced/detailed разными (`plan.style_policy: per_variant`; `first` — первый паттерн пула у всех), титул и финал в тон разделителя; серии одинаковых композиций разбавляются сначала братьями по группе образцов, затем другими кандидатами; содержательные тезисы делятся на пакеты по разделам, для каждого тезиса код отбирает кандидатов-композиций по подаче, вместимости и поддерживаемой визуализации (`matching.py`: таблица только при слоте таблицы, диаграмма — при слоте диаграммы или картинке диаграммы в образце), а модель получает пакет тезисов с фактами, короткий список композиций с ёмкостью и правила варианта и выбирает группировку и формулировки, ссылаясь на факты через `{fact:<id>}`; пакеты идут параллельно под общим deadline, негодный пакет повторяется с подсказкой отдельно. Слоты, подстановку фактов и измерение по файлам шрифтов рендерера выполняет код (`capacity.py`): при переполнении — более вместительная композиция, кегль из шкалы шаблона, сокращение без потери фактов, разделение слайда в пределах диапазона; невозможность разместить обязательное при точном числе слайдов — структурированная ошибка, а не тихая потеря. Планы проверяются валидаторами связей (слоты, факты, число слайдов, покрытие тезисов), сравниваются по последовательности композиций и визуализации — содержательных слайдов отдельно, чтобы разные разделители не маскировали одинаковое содержание (пары без различий записываются предупреждением `variants_indistinct`); разнообразие колоды измеряет `scripts/deck_diversity.py` по планам и ComposedDeck (доля самой частой композиции, серии, стили разделителей, иконки из плана, расстояние между вариантами; строки «до/после» в [docs/evaluation.md](docs/evaluation.md)) и кэшируются в `data/plan-cache` по StoryPlan, структуре и ёмкости паттернов, метрикам шрифтов, настройкам и версиям скилла.

## Вёрстка PPTX

```bash
uv run -m presentation_designer.cli compose runs/plan/balanced.json --profile runs/analyze/profile.json \
    --template tests/fixtures/pptx/mini_template.pptx --content runs/import/package.json --out runs/compose/balanced/
# --prune-layouts убрать неиспользуемые макеты, --pdf ещё и PDF через ONLYOFFICE, --report отчёт
```

Композер (`src/presentation_designer/layout/compose.py`) берёт исходный PPTX как основу: для каждого слайда плана клонирует образец паттерна с графом связей (макет общий, картинки разделяются, диаграммы с книгами данных копируются), заполняет слоты по `element_ref` — текст с сохранением оформления абзацев и фрагментов и явным кеглем из `fit.size_pt`, факты значениями как в источнике, списки абзацами по маркированному абзацу образца, таблицы по строкам-шаблонам таблицы образца, нативные диаграммы (в слоте chart — данные в диаграмму образца, вместо картинки диаграммы — новая на её месте; так же и с диаграммой, нарисованной руками: ряд столбиков из картинок распознаётся анализатором целиком — `parsing/template/drawn_charts.py` — становится одним слотом chart, а его части перечислены в `chart_parts` паттерна и убираются, когда диаграмма построена; зрение модели тут отвечает только на вопрос «график ли это»: если VLM ставит образцу роль chart, а строгие пороги ряда не сошлись, поиск повторяется мягкими — объекты и область всё равно находит код, поэтому без модели разбор работает так же), схемы из фигур, картинки пакета с crop, иконки шаблона с перекраской масок; незаполненные карточки убираются по `removable_object_ids` вместе с пустыми рамками, статика и логотипы остаются, крошечные слоты (номера шагов) сохраняют текст образца. Образцы удаляются, номера слайдов пересчитываются, пакет проверяется (`layout/integrity.py`), по сохранённому файлу строится ComposedDeck (`layout/composed.py`: объекты, геометрия, вычисленные стили, ресурсы, связь со слотами и блоками, `content_source` у каждого объекта). Требование сохранности профиля: `template_hash` профиля должен совпадать с файлом шаблона.

## ИИ-правки: открытый PPTX и план генерации

В интерфейсе проекта команда `/edit` запускает точечную правку текста офисной копии с проверкой базовой ревизии. Изображения и структуру презентации редактируют в ONLYOFFICE; вложения к команде `/edit` не поддерживаются. Это отдельный путь от правки плана генерации через CLI/API ниже.

```bash
uv run -m presentation_designer.cli edit-slide runs/plan/balanced.json --story runs/import/story.json \
    --profile runs/analyze/profile.json --content runs/import/package.json \
    --slide 5 --instruction "сделай заголовок короче и вынеси 40 % в показатель" --out runs/edit/
# затем compose по runs/edit/plan.json; --report сводка (композиция до/после, переполнения, отказ)
```

API `POST /api/generations/{job}/variants/{variant}/edits` создаёт новую ревизию одного варианта по инструкции к одному слайду. Слой `generation/edit.py` (скилл `slide_editor`) получает план, композицию, соседние слайды, факты и доступные варианты подачи. Новый план проходит сборку слотов, проверку ёмкости и связей, затем compose → export → audit. Факты передаются ссылками `{fact:<id>}`; запрос вне доступных данных или за пределами одного слайда отклоняется с причиной. Этот механизм не синхронизирован с ручными изменениями офисной копии и не является обработчиком обычных вопросов чата.

## Правки объектов через CLI/API

Основной визуальный редактор проекта — ONLYOFFICE. Описанный ниже `slide_patch` — отдельный механизм правок плана генерации; офисные изменения не записываются в `slides[].overrides` и не воспроизводятся пересборкой этого плана.

```bash
uv run -m presentation_designer.cli patch-slides runs/compose/balanced/plan.json --patch runs/patch/patch.json \
    --profile runs/analyze/profile.json --content runs/import/package.json \
    --deck runs/compose/balanced/composed.json --out runs/patch/
# затем compose по runs/patch/plan.json (для правок с источником file — с --uploads data/uploads)
```

Ручные правки объектов готового слайда: текст, кегль, начертание, цвет и выравнивание, положение и размер (в том числе внутри групп), замена картинки или иконки из ресурсов шаблона, материалов пакета или своего файла с перекраской монохромных иконок, удаление объекта (клавиша Delete или кнопка в панели), своя надпись на слайде (кнопка «Текст»), фон слайда (цвет, картинка, «как в макете») и перестановка слайдов. Правки хранятся в плане варианта как `slides[].overrides` и применяются композером после заполнения слота (`src/presentation_designer/layout/overrides.py`), поэтому ревизия воспроизводится из плана, а правка из чата сбрасывает ручные правки только у переделанного слайда (`overrides_dropped`). Документ `slide_patch` (`contracts/schemas/slide_patch.schema.json`) уходит в `POST /api/generations/{job}/variants/{variant}/patches` и создаёт новую ревизию без модели тем же путём, что правка из чата; `edits[]` результата помечает такие правки `origin: editor`. Адрес объекта — `object_id` из ComposedDeck базовой ревизии с охраной `source_object_id`/`slot_id`: несовпадение — правка отброшена с предупреждением. Своя надпись (`op: add_text`) адресуется придуманным редактором `usr_…`: объекта с таким адресом в базовой ревизии нет, номер готовой фигуры выводится из него детерминированно, поэтому пересборка ревизии из плана повторяема, а правки текста и положения той же надписи в том же патче находят её по придуманному адресу. Значения вне токенов шаблона применяются с предупреждением `override_off_template`, текст, не помещающийся после правки, — `override_overflow`. Медиа колоды лежит рядом с ревизией (`media/`, `assets[].artifact`), ресурсы шаблона отдаёт `GET /api/templates/{id}/media/{asset_id}`, а для подложки холста анализ рендерит пустой слайд каждого макета (`previews/layout-<id>.png`).

## Модели

```bash
make llm-smoke          # один реальный вызов модели: ключ и адрес из .env
make llm-probe          # зонд провайдера с отчётом в docs/llm-capabilities.md
make llm-limiter-check  # лимитер из нескольких процессов против Valkey
```

Все вызовы моделей идут через пакет `src/presentation_designer/llm`: клиент на openai SDK с `base_url` провайдера, роли `llm`/`vlm` из `config/models.yaml`, общий для всех воркеров лимитер одновременности, RPM и TPM в Valkey, свои повторы (429, сеть, 5xx, негодный ответ) в пределах deadline, кэш ответов в `data/llm-cache`, записанные ответы для тестов (`tests/fixtures/llm`, режимы `record`/`replay`) и учёт usage по этапам. Скиллы — `skills/<name>/skill.yaml` с версионируемыми промптами; версия промпта входит в ключ кэша и в результат. Возможности endpoint (model ID, JSON-схема, изображения, streaming, рассуждение, одновременность) измеряет зонд, результат — [docs/llm-capabilities.md](docs/llm-capabilities.md); до зонда слои конвейера работают в режиме заглушек.

## Сервер и интерфейс

```bash
make api            # локальный API без Docker: задачи выполняются сразу, Valkey не нужен
make dev-real       # интерфейс на http://localhost:3000, /api проксируется на локальный API
make dev            # интерфейс в режиме заглушек: весь сценарий в браузере без backend
make e2e            # сквозные тесты в Chromium, Firefox и WebKit против статического экспорта
make build          # статический экспорт для сервера (рабочий режим, API того же origin)
```

Сервер — FastAPI, состояние в SQLite, очередь RQ поверх Valkey: воркер анализа и исправлений и три воркера генерации; сервис `asr` распознаёт речь для голосового ввода (веса — `make asr-model`, см. [docs/speech.md](docs/speech.md)). ONLYOFFICE Docs Community 9.3.1 — единый офисный движок для редактора и конвертации PPTX → PDF; миниатюры получаются из PDF. Без настроенного ONLYOFFICE реальный экспорт завершается явной ошибкой, без подмены заглушкой. Встроенный AI-плагин и платный Automation API не используются: чат и генерацию обслуживают backend и очередь проекта.

Режим API интерфейса фиксируется при сборке переменной `NEXT_PUBLIC_API_MODE` (`real` по умолчанию, `mock` для заглушек в браузере). `make dev` и `make e2e` проверяют сценарии с заглушками, а не живую генерацию и Document Server. Для полного стека используйте `make up`; запуск и требования к JWT описаны в документации ONLYOFFICE.

Основные экраны:

- `/` — проекты с миниатюрами и состоянием;
- `/project?id=…` — чат, файлы, бриф и настройки слева, просмотр шаблона или редактор готового PPTX справа;
- `/templates` — библиотека шаблонов; `/templates?id=…` — исходник и результаты анализа: композиции, палитра, шрифты, макеты, ресурсы и профиль;
- `/workspace?job=…` — прежний адрес, перенаправляющий в проект.

Проекты, файлы, бриф, настройки и сообщения хранятся на сервере. `POST /api/chat` принимает идентификаторы проекта и сохранённого сообщения, самостоятельно собирает контекст и сохраняет ответ. При недоступной модели возвращается подсказка по правилам (`source: rules`), о чём интерфейс предупреждает.

## Аудит и текущий статус качества

Аудит не является только заглушкой: детерминированные проверки используют собранную колоду, PPTX и фактический PDF-рендер, в том числе для оценки контраста и подмены шрифтов. Контекстные проверки используют VLM и изображения слайдов. Пропущенные проверки отражаются в покрытии (`not_checked`, `coverage.missing_inputs`); наличие отчёта не гарантирует полноту аудита или визуальную пригодность результата.

По зафиксированной проверке 21.09.2026:

- Целевые backend-тесты: **67 passed**; целевой Chromium-прогон: **12 passed, 1 skipped, 1 failed**. Отдельный живой просмотр шаблона прошёл. Открытый сбой — клавиатурный фокус в меню выбора шаблона; весь frontend-набор не считается зелёным.

## Развёртывание

```bash
make up             # весь стек в Docker Compose на этой машине: http://localhost:8080
make down           # остановить локальный стек
make test-server    # интеграционные тесты API и сквозные тесты интерфейса против сервера (или локального стека)
./deploy/install.sh --target server   # Docker и каталоги на сервере из deploy/server.env
./deploy/deploy.sh --target server    # выкладка: образы с тегом выпуска, миграция, ожидание готовности
./deploy/deploy.sh --target server --rollback   # откат на предыдущий выпуск одной командой
./deploy/backup.sh --target server    # резервная копия: база снимком, загрузки, артефакты, Valkey
./deploy/restore.sh --target server --verify-only   # проверка копии в отдельном каталоге; без флага — восстановление
```

Сервер Ubuntu, Docker Compose: вход Caddy с автоматическим TLS (h1/h2), статический интерфейс, API, воркеры (образ со шрифтами; рендер в отдельном ONLYOFFICE), Valkey; на сервере к базовому compose добавляется `docker/compose.prod.yaml` с пределами памяти по замерам, ротацией логов и слотами рендера. Сборка мусора хранилища и артефактов идёт периодической задачей воркера анализа по срокам из `config/app.yaml`. Адрес и SSH-доступ задаются в `deploy/server.env` по образцу `deploy/server.env.example` и в Git не попадают. Подробности: [docs/deploy.md](docs/deploy.md), замеры запуска — [docs/evaluation.md](docs/evaluation.md).

## Ограничения

- Режим выполнения смотрите в `execution_mode`, полноту аудита — отдельно в его покрытии. Реализованный слой не означает, что все проверки выполнены и качество подтверждено. Без настроенного ONLYOFFICE реальный экспорт завершается явной ошибкой, без подмены заглушкой.
- Потоковое появление отдельных слайдов в активной офисной сессии не реализовано. Доступен ранний просмотр целиком опубликованного варианта.
- История чата сохраняется, подсказки-кнопки после перезагрузки страницы — нет. Повторный `POST /api/chat` не дедуплицируется; автоматические повторы этого запроса не включены. Отдельная детерминированная регрессия на сохранение сообщения до задержанного обращения к ассистенту ещё нужна.
- Схемы строятся из нативных фигур и соединителей, а не как объект SmartArt; внешние библиотеки иконок (`icon.query`) и генерация изображений (`image.generate`) не подключены — слот сохраняет иконку образца с предупреждением.
- Шрифты рендерера: в образе воркера есть Play, Montserrat, Poppins, шрифты Microsoft «Core fonts» (Arial, Times New Roman, Courier New, Verdana, Georgia…), Liberation, Carlito, Caladea, Noto, DejaVu; проприетарные шрифты без лицензии на распространение (Consolas, Segoe UI, VK Sans) заменяются с предупреждением `font_substituted` в профиле, метрически совместимые клоны подменой не считаются (`font_metric_equivalent`). В PPTX всегда остаётся исходное имя шрифта — PowerPoint показывает свой.
- `/edit` правит текст текущего PPTX, не добавляет и не удаляет слайды. Правки структуры и изображений выполняются в ONLYOFFICE. Отдельный API правки плана генерации ограничен одним слайдом одного варианта.
- У механизма `slide_patch` собственные ограничения: добавление только текстовых объектов, без редактирования содержимого таблиц, диаграмм и схем и без поворота. Эти ограничения не описывают возможности ONLYOFFICE; офисная копия и план генерации — разные ветки изменений.
- Стиль титула, разделителей и финала внутри колоды единый, чередование стилей внутри колоды не делается; иконки в слотах пока берутся из образца (подбор по смыслу из ресурсов шаблона — этап 15), фото и фоны макетов не заменяются (этап 16).
- Неиспользуемые макеты по умолчанию остаются в файле (`layout.prune_unused_layouts: false`): так в PowerPoint у пользователя доступен полный набор макетов шаблона; включение уменьшает файл VK Education с 17,7 до 0,6 МБ.
- Один арендатор без авторизации: все проекты видны каждому, кто открыл адрес сервиса.
- PDF без текстового слоя (сканы) не распознаются: файл помечается предупреждением, в пакет попадает только изображение страницы.
