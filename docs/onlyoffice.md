# Скачивание и начало проекта

Обновление 21.09: просмотр шаблона в проекте до генерации, подключение ассистента,
команда `/edit` и границы асинхронной оркестрации описаны в
`./docs/onlyoffice-orchestration.md`.

В шапке проекта иконка скачивания открывает компактное меню **PPTX / PDF / HTML**.
Все форматы используют выбранную сохранённую ревизию ONLYOFFICE, а не исходный
артефакт генерации. Перед скачиванием последних ручных правок сохраните документ.
PDF конвертируется через ONLYOFFICE; HTML — автономная страница со встроенными
изображениями слайдов (без внешних ресурсов, не редактируемая HTML-вёрстка).
Экспорт не закрывает редактор и не изменяет сохранённый PPTX.

Выбор шаблона находится в первом автоматическом сообщении чата: можно добавить
PPTX или выбрать ранее загруженный шаблон с миниатюрой. После выбора следующий
шаг — задача и материалы. Существующая история чата и выбранный шаблон сохраняются.

# ONLYOFFICE: единый офисный движок

Извлечение встроенных шрифтов PPTX до рендера и ограничения регистрации:
`./docs/embedded-fonts.md`. Подготовка сохраняет карантин
и отчёт; общий индекс живого Document Server автоматически не обновляется.

Выбран ONLYOFFICE Docs Community 9.3.1, официальный multi-arch Docker-образ
`onlyoffice/documentserver:9.3.1` (локально запущен linux/arm64), дополненный шрифтами
проекта. Это единственный офисный движок для редактора и серверного PPTX → PDF.
LibreOffice удалён из приложения и образов. Automation API не используется.
Лицензия ONLYOFFICE — отдельная от Apache-2.0 приложения; перед публичным выпуском
нужно проверить применимые условия Community/AGPL и выбранную коммерческую схему.

## Запуск

Рабочий каталог: `.`.
В игнорируемом `./.env` должен быть случайный
`PD_ONLYOFFICE__JWT_SECRET` длиной не меньше 32 символов. Один секрет используется
API, воркерами и Document Server. Не выключать JWT. Браузерный URL по умолчанию:
`PD_ONLYOFFICE__PUBLIC_URL=http://localhost:8080/onlyoffice`.

```sh
docker compose \
  -f ./docker/compose.yaml \
  -f ./docker/compose.dev.yaml \
  --env-file ./.env up -d --build
```

ONLYOFFICE входит в базовый Compose. `make up` создаёт секрет при первом запуске
и ограничивает вход Caddy адресом 127.0.0.1, поскольку
приложение пока не имеет пользовательской авторизации. При ручном запуске задайте
`PD_HTTP_PORT=127.0.0.1:8080`, `PD_HTTPS_PORT=127.0.0.1:8443`. У самого Document Server
нет опубликованного порта. Частные IP разрешены только потому, что storage API
находится в сети Compose. Metadata IP не разрешены.

Документация вендора рекомендует от 4 ГБ RAM для Docs; существующий стек также
потребляет память. Не добавлять этот сервис вслепую на существующий сервер с 4 ГБ.

## Интервал отрисовки презентаций: 16 мс

21 сентября после повторной проверки пользователь попросил вернуть 40 → 16 мс.
`./scripts/patch_onlyoffice_rendering.py` меняет только
`this.O_i=new AscCommon.hpf(40,B);` в SDK презентаций 9.3.1 build 10. Остальные
таймеры, autosave, анимации приложения и опрос документа не меняются. Это настройка
интервала, а не гарантия 60 FPS на любом устройстве.

Скрипт проверяет SHA-256 обоих исходных JS до записи, отказывается от неизвестной
сборки, допускает повторный запуск, сохраняет резервные копии и синхронные `.gz`.
Он включён в `./docker/onlyoffice.Dockerfile`.
Локально применён без перезапуска Document Server. Хэш SDK после патча:
`5ad873396344deedf33b03fb81a1b0421108ac4d7160dd58b6ca6d77c7ee90e7`.

`api.js` использует новый namespace ресурсов `9.3.1-118841e3cd9116f13e5f1bdcf35ae068_pd16v2`,
а приложение запрашивает API с `?rendering=pd16v2`. Это отделяет новые запросы от
HTTP/Service Worker кэша старого SDK. Уже открытые iframe сохраняют прежний код:
сначала сохраните документы и дождитесь подтверждения, затем обновите страницу.
Не очищайте всё хранилище сайта: там могут быть черновики приложения.

Для отката восстановите `sdk-all.js`, `api.js` и оба `.gz` из
`/var/www/onlyoffice/rendering-backup-40ms` в соответствующие каталоги Document Server,
уберите вызов патча из Dockerfile и смените cache version при публикации. Не
перезапускайте Document Server ради обновления статических файлов. Оригинальные хэши
заданы в скрипте; тесты — `./tests/test_onlyoffice_rendering_patch.py`.

## Шаблоны: анализ отдельно от исходного PPTX

Библиотека `/templates` показывает поиск, статусы и палитры. Внутри шаблона находятся
«Стиль» (дизайн-система и правила оформления), «Слайды» (просмотр исходного PPTX)
и «О файле» (ресурсы, макеты и технические результаты анализа). Классификация слайдов
и композиции остаются в профиле для генерации, но не имеют отдельных вкладок.

«Смотреть слайды» / «Слайды» запускает ONLYOFFICE только по запросу пользователя.
`POST /api/office/templates/{id}/config` возвращает подписанный `mode=view` с
`permissions.edit=false`, без callback сохранения. Исходник отдаётся Document Server
по JWT с отдельной областью `office-template`, ID, SHA-256 и сроком действия.
Просмотр не создаёт офисные копии/ревизии и не меняет профиль. При отключённом
ONLYOFFICE этот режим скрыт; скачивание исходника через меню работает независимо.

Нельзя редактировать исходник поверх уже рассчитанного профиля: это рассинхронизирует
генерацию и правила. Для изменения шаблона скачайте PPTX, отредактируйте и загрузите
изменённый файл заново — он получит новый анализ. Авторизация пользователей остаётся
общим ограничением локального стенда, JWT защищает сервисную выдачу, не пользователей.

## Упрощённый интерфейс редактора

В подписанной конфигурации редактора отключены плагины (`plugins: false`, включая
встроенный AI ONLYOFFICE), макросы, справка, обратная связь и предложения функций.
ИИ приложения остаётся отдельным рабочим процессом. Компактный заголовок не
дублирует имя файла; инструменты слайдов, комментарии, печать, autosave и force-save
не отключены. Отключение плагинов и макросов функциональное, а не только визуальное.

Вкладка «Файл» и штатный логотип пока сохранены. Документированный параметр
`customization.layout.toolbar.file` относится к расширенной white-label лицензии
Docs Developer; установленная Community 9.3.1 проверяет доступ к `layout`.
Перенос брендинга вниз требует отдельного согласования лицензии и реализации:
не добавляем игнорируемые параметры и не изменяем лицензионные проверки редактора.

Изменения конфигурации применяются при следующем создании iframe после обновления
API. Уже открытый редактор не пересоздаётся. Для этой правки не требуется менять
образ или перезапускать Document Server; активные сессии не закрывать ради проверки.

Документация параметров:
- https://api.onlyoffice.com/docs/docs-api/usage-api/config/editor/customization/customization-standard-branding/
- https://api.onlyoffice.com/docs/docs-api/usage-api/config/editor/customization/customization-white-label/

## Рабочий процесс

1. Создать презентацию существующим ИИ-генератором, дождаться окончания задания.
2. На странице проекта готовый PPTX автоматически открывается справа в единственном
   редакторе. Это настоящий ONLYOFFICE со своей лентой миниатюр и инструментами,
   а не HTML-копия слайдов. Чат и файлы проекта остаются слева.
3. Создаётся офисная копия конкретного PPTX. Повторное открытие того же исходника
   возвращает ту же офисную копию. Режим ИИ-исходника, старый редактор, отчёты аудита
   и их скачивания убраны из интерфейса проекта. Служебные проверки на сервере сохранены.
   Новая генерация не заменяет открытый офисный файл: сначала завершите редактирование,
   затем явно откройте новую версию через меню действий.
4. Редактировать в ONLYOFFICE. Кнопка сохранения инициирует force-save; callback
   статуса 6 сохраняет снимок, не меняя ключ активной сессии.
5. **⋯ → Завершить редактирование** закрывает iframe. После закрытия всех подключений
   ONLYOFFICE присылает финальный callback (2) или закрытие без изменений (4).
6. Скачать нужную **сохранённую** версию. v0 — исходные байты ИИ; v1 и далее —
   подтверждённые сохранения. Скачивание не вызывает повторную сборку PPTX.
   Кнопка над редактором скачивает офисную версию. История сохранений и выбор варианта
   находятся в меню **⋯**. Выбор сохранённой версии относится только к скачиванию,
   а не к содержимому открытого редактора. Смена варианта заблокирована до закрытия сессии.
   Выбор слайда в ONLYOFFICE не синхронизирован с индексом слайда ИИ-модели, поэтому
   правка слайда из чата адресуется номером в самой фразе («на слайде 3 …»).

Подпись callback проверяется, используются только подписанные поля, URL сохранения
ограничен cache/files настроенного сервиса; HTTP redirects запрещены. Размер и
OOXML проверяются перед фиксацией. `error:0` возвращается только после транзакции.
Старый ключ не может перезаписать новую сессию. Повтор одинакового сохранения
не создаёт дубликат ревизии.

## Готовая презентация: показ сразу, разбор в фоне (24.09.2026)

«Открыть как презентацию» делает три запроса: шаблон, содержание и задание варианта
`original`. Задание приходит с уже опубликованной ревизией r1 — это копия загруженного файла
байт в байт, которую `submit_generation` публикует сам, без очереди и модели (на сервере
около 0,1 с). `ProjectOffice` создаёт офисную копию r1 первым же опросом, и слайды видны,
как только ONLYOFFICE откроет файл. Скрипты редактора прогреваются (`warmUpOffice`) сразу по
ответу «Открыть как презентацию», пока файл ещё загружается.

Всё остальное идёт в фоне и не мешает ни показу, ни ручным правкам:

- очередь `interactive` (воркеры генерации берут её первой): подписи пустых плейсхолдеров,
  диаграммы-картинки → ревизия r2, затем PDF и миниатюры последней ревизии;
- разбор шаблона (`analysis`) и импорт содержания (`generation`), затем смысловой план по
  профилю и полная сборка варианта (план, `composed.json`, аудит) в последнюю ревизию. Без
  модели это около 8 с, поэтому план и сборка тоже идут в `interactive` и не ждут чужих
  сборок. Контекстный аудит при открытии выключен (`run_contextual_audit: false`); проверить
  слайды моделью можно из подробностей задания в чате — такое задание собирается в
  `generation`.

Чат: под «Открываю «X» как готовую презентацию…» до сигнала редактора — только таймер и
«Открываю презентацию», затем итог «Презентация открыта за N с». Разбор в фоне — тихая
строка с процентом задания и сроком: «Разбираю презентацию в фоне: правки из чата — через
~40 с». Когда появляется r2, строка «Сделал диаграммы редактируемыми: N (слайды …)».

Переключение ревизий. Новая версия того же задания (r2 с диаграммами, ревизия правки из
чата) или новое задание открываются в редакторе сами, если документ ещё не правили: у него
нет сохранённых версий (revision 0) и ONLYOFFICE не присылал `onDocumentStateChange` с
несохранёнными изменениями. Ключ сессии (`active_key`) ONLYOFFICE ставит при любом открытии,
поэтому признаком правки он не служит. Если правки были, документ остаётся, а над
редактором баннер «Доступна другая версия презентации».

Правки из чата. В редакторе слайд для чата не выделить, поэтому номер берётся из фразы:
«на слайде 3 сократи текст», «3-й слайд — крупнее заголовок». Пока у последней ревизии нет
плана, сервер принимает правку, ставит её за сборкой варианта (`depends_on`, итог задания
она не ждёт) и перед запуском переносит базу на последнюю ревизию; чат отвечает «Разбираю
презентацию, правку применю через ~N с». Если задачи разбора стоят за чужими сборками
(всё, чего они ждали, готово, а начаться не могут дольше 8 с), срока нет, и фраза честно
говорит «очередь занята другими сборками, правку применю сразу после разбора». Прямая правка офисного документа (`/edit`, логотип, выбранные объекты)
и ручные правки в ONLYOFFICE доступны сразу. Если разбор в фоне не удался, чат говорит, что
правки из чата недоступны, а редактор и скачивание работают; «Повторить разбор» — кнопкой в
ленте.

## Правка выбранного слайда и объекта из чата (24.09.2026)

Живой редактор сообщает приложению, какой слайд открыт и что выделено, — через свой внутренний
API в том же окне, что и сохранение (`frontend/lib/editor/officeLive.ts`; коннектор Automation
API есть только в платной редакции). Разведка на izbox.ru (ONLYOFFICE 9.3.1): щелчок по
миниатюре — событие `asc_onCurrentPage` с номером слайда с нуля, `getCurrentPage()` отдаёт то же;
выделение — `asc_onFocusObject` и `getSelectedElements()` с типами из
`Asc.c_oAscTypeSelectElement` (7 — слайд, 6 — фигура, 0 — абзац); у фигуры публичные
`asc_getName()` (имя `cNvPr`), `asc_getPosition()`, `asc_getWidth()/asc_getHeight()` в
миллиметрах. Номера фигуры в PPTX (`cNvPr id`) редактор наружу не отдаёт, объекты документа в
сборке минифицированы, API макросов (`window.Api`) в окне нет. Нет нужных методов (другая версия
редактора) — моста нет, и всё работает как раньше: слайд для правки берётся из фразы «на слайде N».

В чате над полем — плашка адресата:

- **слайд** («Слайд 3 · Сбалансированный», подсказка «Что изменить на слайде 3?») — правка
  слайда моделью по плану варианта (`POST …/variants/{variant}/edits`, как «на слайде 3 …»).
  Новая ревизия варианта не подменяет открытую копию: если копию правили руками, пересобранный
  слайд переносится в неё (`POST /api/office/documents/{id}/apply-slide`,
  `layout/merge.py: replace_slide` — части слайда, картинки, диаграммы, макет по имени, та же
  запись `sldId`), редактор сохраняет несохранённое, закрывается, получает новую ревизию копии и
  открывается на том же слайде. Ручные правки остальных слайдов остаются, правки самого слайда
  заменяются пересобранным. Не правили — редактор переключается на новую ревизию целиком, как
  раньше. Число слайдов в редакторе не совпадает с планом (слайды добавлены или удалены
  вручную) — чат честно говорит, что пересобрать слайд нельзя, и предлагает выделить объект;
  перестановку без изменения числа слайдов проверка не ловит;
- **объект** («Слайд 3 · «Идея: плотность в центре…»») — правка только его, по схеме `/edit`
  (сохранение → закрытие → правка → открытие), без перехода в превью. Сервер находит фигуру в
  сохранённой копии по слайду и имени, при одинаковых именах — ближайшую по рамке
  (`office_objects.resolve_live`, поле `live_target` запроса `…/edit`); подпись для плашки —
  текст объекта из карты сохранённой ревизии. Несколько выделенных фигур ONLYOFFICE сводит в одну
  запись без имени — тогда адресат слайд.

Крестик на плашке снимает адресацию до следующего выбора в редакторе. Правка из чата остаётся
в дизайне выбранного шаблона: в режиме «Смешанный» она выбирает только композиции шаблона, а
встроенную — лишь ту, на которой слайд уже стоит (`generation/edit.py: edit_pool`; в режиме «Все
слайды новые» встроенные остаются). Просят колонки или дизайн шаблона («дизайн не меняй,
оставляй как был») — уходит и текущая встроенная: слайд возвращается в композицию шаблона,
встроенная сетка — в сетку шаблона на столько же мест, отказ «менять нечего» модели не
принимается, пока в шаблоне есть куда переложить слайд. Правка понимает названное число элементов («не 4 колонки, а
2», «в две колонки», «оставь три карточки», «колонки сделаем не три а две», «не три варианта, а
два», «колонки две, а не три»): «чистые» сетки ровно на столько мест идут в кандидаты сразу за
текущей и названы модели по идентификаторам; ответ с другой композицией получает первую из них, и
подгонка по объёму выбирает только среди них (`requested_count`, `grid_rank`). Сетка шаблона на
больше мест (у VK Tech «Три текстовых блока») приходит в подбор сокращённой до названного числа
(`reduced_view`): слоты лишних карточек сняты, оставшиеся — такой ширины и высоты, какими их
сделает сборка, поэтому ёмкость считается по широким карточкам. Сборка убирает пустые карточки и
раскладывает оставшиеся на всю ширину ряда (`layout/compose.py: _reflow_cards`,
`generation/reflow.py`): подложки и тексты шире с прежними полями, иконки и точки держатся своего
края, текст, прижатый к верху, растёт вниз до иконки своей карточки; ряд в группах фигур, с
соединителями или с объектами между карточками остаётся как был, режим «По шаблону» блоки не
двигает. Просили только переложить по местам — текст прежний: какие пункты куда, решает модель,
а тексты карточек собираются из прежних пунктов дословно (`regroup_items`); потеряла пункт —
прежние пункты склеиваются по соседству (`merge_items`); заголовок, о котором не просили, и
иконки карточек остаются прежними. Нет подходящей сетки в шаблоне — отказ с причиной; подсказка
«данные не выдумываю» в чате — только к отказу из-за данных. Нарушения, которые в плане уже были
до правки (пустое обязательное место на другом слайде сборки), правку не блокируют — отклоняется
только то, что внесла она сама. Тезисы-разделы модели не показываются, и ссылки на них правка
переносит на новый слайд сама: обязательный раздел, который держится только на этом слайде,
иначе оставался бы непокрытым.

## ИИ-правка текущего PPTX (21.09.2026)

Текстовое сообщение в чате при открытом офисном документе теперь направляется в
`POST /api/office/documents/{id}/edit`, а не в старый редактор плана генерации.
Первая реализация поддерживает **только точечные изменения текста**. Изменения
структуры, изображений и геометрии не реализованы; модель должна возвращать отказ
или уточняющий вопрос без патчей. Нельзя считать это произвольным ИИ-редактором PPTX.

Последовательность:

1. Ручное редактирование временно приостанавливается. Iframe остаётся живым до
   отправки изменений; затем вызывается `requestClose`, и только после подтверждения
   он закрывается. При ошибке/тайм-ауте отправки документ остаётся открытым.
2. Приложение ждёт финального callback и отсутствия `active_key`. Force-save или
   `onDocumentStateChange(false)` сами по себе недостаточны. Другая открытая вкладка
   блокирует правку; после 90 секунд ожидания запрос отменяется без перезаписи.
3. Сервер захватывает эксклюзивную SQLite-аренду на 240 секунд и проверяет ревизию.
   Повторное открытие документа и вторая ИИ-правка получают 409. Модель имеет бюджет
   180 секунд; просроченная аренда не позволяет зафиксировать результат.
4. Модель получает текст **сохранённого PPTX** в фактическом порядке слайдов.
   Сервер проверяет адрес каждого текстового узла и точное совпадение старого текста.
   Изменяются только узлы `a:t` в явно затронутых XML слайдов; остальные ZIP members
   сохраняют исходные распакованные байты. План генерации не используется.
5. Новая неизменяемая ревизия записывается в тот же документ. Редактор автоматически
   открывается с новым ключом. Предыдущие ревизии остаются доступны для скачивания.

Ограничения: семантический выбор текста делегирован модели, результат нужно проверять;
длинный новый текст может переполнить исходный блок. Перекомпоновки, проверки fit,
визуального аудита и подтверждения предлагаемого diff в этом пути пока нет.
Импорт вложений вместе с запросом правки не поддерживается — UI объясняет ограничение.
Полная новая генерация и смена варианта остаются отдельными действиями и не являются
способом править текущий документ с сохранением ручных изменений.

Проверки реализации: 44 серверных теста прошли, включая точность незатронутых частей
PPTX, сохранение ручного форматирования/позиции и соседнего слайда, новую ревизию
того же документа, конфликты, истечение аренды и снятие блокировки при ошибке.
TypeScript, ESLint изменённых файлов, production build и mypy трёх серверных модулей
прошли. Логи: `/tmp/mai-office-unified-backend.log`,
`/tmp/mai-office-unified-build.log`, `/tmp/mai-office-unified-browser.log`.
Браузерные тесты изолированной production-сборки: **12 passed, 3 skipped** в
Chromium/Firefox/WebKit. Новый тест проверяет ожидание финального сохранения,
передачу его ревизии в `/edit` и автоматическое открытие того же документа.
Настоящий цикл ручная правка → реальная модель → повторное открытие в Document Server
для этой реализации пока **не проверен**; mock-SDK тест не заменяет такую приёмку.
Эта доработка пока не развёрнута на `localhost:8080`: при проверке обнаружена одна
активная офисная сессия; API и рабочий frontend не перезапускались.

## Картинка из «Файлов» на слайд (24.09.2026)

Карточку картинки из панели «Файлы» (вкладка «Загруженные» — PNG/JPEG проекта, вкладка
«Из шаблона» — растровые ресурсы профиля) можно перетащить на открытый редактор.
Iframe Document Server сам события перетаскивания родителю не отдаёт, поэтому на время
перетаскивания над ним лежит прозрачная крышка `office-drop`; что тащат, хранит
`lib/state/drag.ts`. Бросок вызывает `POST /api/office/documents/{id}/images` с
`{project_id, file_id}` или `{template_id, asset_id}`. Сервер проверяет источник (файл
этого проекта, проверенная картинка PNG/JPEG; ресурс из профиля шаблона PNG/JPEG/GIF/BMP)
и отвечает командой `{c: "add", images: [{fileType, url}], token}`: `url` — внутренний
адрес API (`storage_url`, `/api/projects/{id}/files/{file_id}/content` или
`/api/templates/{id}/media/{asset_id}`), `token` — подпись `{c, images}` секретом
ONLYOFFICE. Страница передаёт команду в `docEditor.insertImage`, Document Server сам
скачивает картинку и ставит её на текущий слайд; сохраняется она обычным путём редактора.
Ошибки: `404 office_not_found` / `file_not_found` / `template_not_found` /
`asset_not_found` / `file_missing`, `422 file_not_image`.

Приёмка на izbox.ru: PPTX открыт как презентация, на первый слайд брошены PNG из
«Загруженных» и ресурс шаблона, «Сохранить и превью» дало ревизию 1; в скачанном PPTX
на первом слайде 3 картинки вместо 1, байты PNG совпадают с загруженным файлом.

## Границы прототипа

- PPTX хранится отдельно от ComposedDeck, но новая текстовая ИИ-правка и ONLYOFFICE
  меняют один офисный документ. Аудит/PNG/PDF старого генератора не отражают этих
  изменений. Новая полная генерация создаёт другой исходник, не перезаписывает
  текущий офисный документ. Ссылку `/office?id=…` можно сохранить.
- Внутри ONLYOFFICE отключено скачивание, чтобы не выдавать несохранённое состояние
  за серверную версию. Кнопка над редактором скачивает точные байты выбранной версии.
- База копий: `/app/data/onlyoffice.sqlite3` в томе приложения. Байты и метаданные
  пишутся одной SQLite-транзакцией. Офисные копии не удаляет GC генераций.
  **Штатный backup/restore приложения пока не интегрирован с этой отдельной БД**:
  для резервирования используйте SQLite backup API отдельно, а не копирование
  открытого файла; восстановление офисных данных нужно проверять отдельно.
- Пока нет каталога всех офисных копий, квот/удаления, импорта обратно в ИИ,
  восстановления зависшего ключа через command service.
  Не считать этот стенд готовым production-хранилищем документов.
- Callback одной сессии фиксируются в порядке завершения скачивания. Порядок
  конкурентных force-save не проверяется по времени редактора; это ограничение
  прототипа, а не гарантия упорядочивания всех параллельных сохранений.
- При ошибке сохранения не закрывать вкладку. Скачивание старой версии не является
  подтверждением сохранения текущих изменений.
- Полная визуальная эквивалентность PowerPoint требует ручного round-trip на трёх
  шаблонах; установка редактора сама по себе её не гарантирует.

### Серверный рендер

`export/pdf.py` отправляет подписанный JWT запрос `POST /converter` с `async: true`,
`filetype: pptx`, `outputtype: pdf` и уникальным ключом. Опрос использует тот же ключ.
Вход — временная копия в общем томе `/app/data/office-conversions`, доступная только
через короткоживущую подписанную ссылку `/api/office/conversions/{key}`. Ни офисной
ревизии, ни сессии редактора при этом не создаётся. Исходный PPTX не меняется.
Копия удаляется при успехе и ошибке; остатки убитых воркеров старше двух часов
убираются при следующей конвертации. Максимальный бюджет конвертации — один час.

PDF скачивается только из `/cache/files/` настроенного Document Server, без redirects,
с лимитом `onlyoffice.max_pdf_mb` (200 МБ), проверяется PDFium и публикуется атомарно.
Общий бюджет — `timeouts.render_convert_s`; ошибки возвращаются явно, без fallback
на другой офисный движок или заглушку. ONLYOFFICE не предоставляет здесь отмену
серверной задачи: после клиентского тайм-аута сервер может ещё завершать конвертацию.

Экспорт ревизий, предварительный рендер, анализ шаблонов/макетов и startup-check
проходят через этот конвертер. PNG делает PDFium; HTML продолжает строиться из
ComposedDeck. Аудит получает те же PNG/PDF. Общие слоты Valkey (`render.slots=2`)
ограничивают запросы воркеров, но не число пользователей редактора.
API и воркеры обязаны разделять том данных и JWT secret. Воркеры ждут готовности
API и ONLYOFFICE, затем проверяют реальную конвертацию тестового PPTX и миниатюру.
Версия анализатора повышена: старые превью не должны переиспользоваться как новые.

Для CLI вне Docker нужен запущенный API с **тем же каталогом данных**, доступным
для CLI; `internal_url` должен быть доступен CLI, `storage_url` — Document Server.
Проще запускать CLI через `docker compose exec worker-generation …`.

Шрифты Play/Montserrat копируются в оба образа; Carlito, Caladea, Liberation,
DejaVu и Noto установлены в обоих. После их изменения пересоберите
воркеры и ONLYOFFICE. Встроенные/системные шрифты могут отличаться; визуальное
совпадение с PowerPoint не гарантируется и требует ручной проверки.

Новые тесты: `tests/export/test_pdf.py` — JWT, polling, тайм-аут, SSRF,
лимит размера, валидность PDF, атомарная публикация, очистка и неизменяемый исходник.
