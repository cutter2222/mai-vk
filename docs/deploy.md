# Развёртывание

Сервис работает на сервере Ubuntu в Docker Compose. Код живёт в репозитории, на сервере руками ничего не правится: любое изменение попадает туда через `deploy/deploy.sh`, который записывает выпуск (тег образов, commit, признак незакоммиченных изменений, версия схемы) в `$SERVER_DIR/deploys.log`. Сервер заменяем: на нём только образы, собранные из репозитория, `.env` с настройками и данные в `$SERVER_DIR`.

Сервисы стека (`docker/compose.yaml`, на сервере плюс надстройка `docker/compose.prod.yaml`):

| Сервис | Образ | Назначение | Предел памяти на сервере |
| --- | --- | --- | --- |
| `caddy` | `caddy:2.11.4-alpine` | вход: TLS, `/api/*` → API, остальное → интерфейс; `www.` → основной адрес; только h1/h2 | 192 МБ |
| `frontend` | `presentation-designer/frontend:<тег>` | статический экспорт Next.js в рабочем режиме | 64 МБ |
| `api` | `presentation-designer/api:<тег>` | FastAPI: проекты, файлы, шаблоны, содержание, задания, артефакты; SQLite в `data/`; CLI обслуживания | 512 МБ |
| `worker-analysis` | `presentation-designer/worker:<тег>` | очереди `analysis` и `repair`: анализ шаблонов (ONLYOFFICE/PDFium для миниатюр, VLM для ролей образцов и тегов иконок), исправления, периодическая сборка мусора | 1,5 ГБ |
| `worker-generation` ×3 | `presentation-designer/worker:<тег>` | очереди `interactive generation` (порядок — приоритет): фон открытой презентации, импорт, смысловой план, варианты; шрифты для измерения текста; число реплик — `PD_GENERATION_WORKERS` | 1,5 ГБ каждый |
| `asr` | `presentation-designer/asr:<тег>` | распознавание речи для голосового ввода (GigaAM int8, ONNX Runtime, одно ядро); веса — `$SERVER_DIR/models` (`PD_MODELS_DIR`, доставляет `make asr-model`), без них сервис жив, а кнопки микрофона нет; модель грузится по первой фразе и выгружается после 10 минут простоя | 768 МБ (`PD_ASR_MEMORY`) |
| `onlyoffice` | `presentation-designer/onlyoffice:<тег>` | редактор и PPTX → PDF; Docs 9.3.1 со шрифтами проекта | 4 ГБ |
| `valkey` | `valkey/valkey:8.1-alpine` | очередь RQ, лимитер запросов к провайдеру моделей (общий для всех воркеров), блокировки; AOF раз в секунду, `maxmemory 128mb noeviction` | 256 МБ |

Данные: `$SERVER_DIR/data` (SQLite `state.sqlite3`, загрузки `uploads/<sha256>`, материалы организаторов `organizers/`, кэш ответов модели `llm-cache/`, кэш разбора материалов `import-cache/` и кэш готовых планов вариантов `plan-cache/` — производное состояние, в копию не входит), `$SERVER_DIR/runs/tmp` (временные каталоги рендера при анализе шаблонов), `$SERVER_DIR/artifacts` (артефакты заданий по ревизиям, превью шаблонов), `$SERVER_DIR/runs` (отчёты, в том числе `gc/last.json`), `$SERVER_DIR/backups` (резервные копии), `$SERVER_DIR/releases` (копии репозитория последних выпусков для отката). Каталоги данных принадлежат пользователю сервиса, контейнеры работают от него же (`PD_UID`/`PD_GID` в `.env`). Наружу опубликованы только порты 80 и 443 Caddy; API, Valkey, база и хранилище доступны только контейнерам стека.

## Требования к серверу

- Ubuntu 22.04 или 24.04 (подходит и Debian 12), архитектура x86_64 или arm64.
- SSH по ключу: root либо пользователь с `sudo` без пароля.
- Открытые порты 80 и 443 (TCP). Внутренние порты сервисов наружу не публикуются, UDP 443 не нужен: HTTP/3 выключен.
- Адрес для HTTPS: свой домен с A-записью на сервер или имя вида `203-0-113-10.sslip.io` (точки IP заменены дефисами, домен не нужен). Сертификат Caddy получает и продлевает сам. Без HTTPS браузер не регистрирует service worker режима заглушек, а в рабочем режиме TLS нужен для загрузок и прямых ссылок.
- ONLYOFFICE требует отдельного бюджета памяти (рекомендация вендора — от 4 ГБ для Docs), плюс API, воркеры и очередь. Для всего стека ориентир — от 8 ГБ RAM с последующей нагрузочной проверкой, не гарантия для любого числа пользователей. Старые замеры LibreOffice неприменимы. `PD_RENDER_SLOTS=2` ограничивает запросы конвертации, но не сессии редактора. Предел ONLYOFFICE задаётся `PD_ONLYOFFICE_MEMORY` (4G); swap не заменяет RAM. Для сервера с 4 ГБ сначала увеличьте ресурсы или вынесите Docs отдельно.
- Настройки в `.env` сервера: `PD_GENERATION_WORKERS` (реплики воркеров генерации), `PD_RENDER_SLOTS` (слоты рендера, попадают в приложение как `render.slots`), при необходимости `PD_WORKER_MEMORY` и `PD_API_MEMORY` (пределы контейнеров, по умолчанию `1536M` и `512M`).
- `PD_ONLYOFFICE__JWT_SECRET` создаётся установщиком/выкладкой при отсутствии; один секрет у API, воркеров и Docs. API и воркеры разделяют `data/` для краткоживущих источников конвертации. Воркеры ждут готовности API и Docs, затем проверяют реальный PPTX → PDF → PNG. Подробности и ограничения офисного хранилища: [onlyoffice.md](onlyoffice.md). До реализации пользовательской авторизации не публикуйте редактор в открытый Интернет.

## Параметры сервера

Скопируйте `deploy/server.env.example` в `deploy/server.env` и заполните:

| Переменная | Значение |
| --- | --- |
| `SERVER_SSH` | `пользователь@хост` или алиас из `~/.ssh/config` |
| `SERVER_DIR` | корень сервиса, по умолчанию `/srv/presentation-designer` |
| `SERVER_URL` | объявленный адрес, только `https://…` |
| `SERVER_ALIAS_URLS` | необязательно: запасные адреса через запятую, которые Caddy обслуживает вместе с основным (например, `https://www.example.com,https://203-0-113-10.sslip.io`); имена с `www.` перенаправляются на `SERVER_URL` |

Файл в Git не попадает. Переезд на другой сервер — новый `deploy/server.env` и те же команды (сценарий ниже).

## Установка

```bash
./deploy/install.sh --target server
```

Ставит Docker Engine и compose plugin из репозитория Docker, на машинах с памятью меньше 8 ГБ создаёт swap 2 ГБ, создаёт системного пользователя `presentation-designer`, каталоги `$SERVER_DIR/{repo,data,artifacts,runs,backups,releases}` и файл `$SERVER_DIR/.env` (в нём `PD_GENERATION_WORKERS=3`, `PD_RENDER_SLOTS=2`). В конце печатает версии Docker, число ядер, память и свободное место. Повторный запуск безопасен. Обновление пакетов системы и отключение входа по паролю остаются за администратором сервера; `unattended-upgrades` в Ubuntu ставит обновления безопасности сам.

Секреты провайдера моделей вписываются в `$SERVER_DIR/.env` на сервере вручную, образец — `config/.env.example`: `PD_QWEN_BASE_URL` (OpenAI-совместимый endpoint, `…/v1`) и `PD_QWEN_API_KEY`. Значения-образцы (`example.invalid`, `replace-me`) клиент не принимает — провайдер считается ненастроенным, `/api/health` показывает `provider.configured: false`. Строки `PD_PUBLIC_URL`, `PD_SITE_ADDRESS`, `PD_HTTP_PORT`, `PD_HTTPS_PORT`, `PD_*_DIR`, `PD_ENV_FILE`, `PD_IMAGE_TAG` и `PD_BUILD_COMMIT` в этом файле переписывает `deploy.sh`, остальное сохраняется. Ключи в логи контейнеров, отчёты и `/api/health` не попадают — только хост провайдера.

Материалы организаторов (`data/organizers`) на сервер и в резервную копию не входят и в Git не попадают. Они восстанавливаются копированием с машины разработчика:

```bash
make organizer-data                                      # docs/ → data/organizers с манифестом
scp -r data/organizers root@сервер:/srv/presentation-designer/data/
```

## Выкладка и обновление

```bash
./deploy/deploy.sh --target server    # или make deploy
```

1. Отправляет на сервер ровно те файлы, которые видит `git ls-files` с учётом `.gitignore`: без `.git`, локальных планов, материалов организаторов и `.env`. Дерево в `$SERVER_DIR/repo` заменяется целиком, устаревших файлов не остаётся.
2. Записывает адрес из `SERVER_URL` в `.env` сервера. Адрес не зашит в образы: интерфейс обращается к API того же origin, Caddy берёт имя сайта из переменной `PD_SITE_ADDRESS`.
3. Собирает образы с тегом выпуска `<commit>[-dirty]-<время>` (`docker compose build` с базовым и прод-файлами Compose; базовые образы закреплены точными тегами, принудительный `--pull` не используется — он упирается в лимит анонимных запросов Docker Hub).
4. Применяет миграции состояния новым образом до запуска контейнеров: `python -m presentation_designer.cli.maintenance migrate`. Если у базы недостающие версии схемы, перед миграцией создаётся полная резервная копия (`backups/backup-<время>-pre-migrate-<тег>.tar`), к которой возвращает откат. Без изменений схемы копия не делается.
5. Поднимает стек (`docker compose up -d --remove-orphans`): пересоздаются только сервисы, чьи образы или настройки изменились. Затем ставит на повторный анализ шаблоны библиотеки, чей профиль устарел с этим выпуском (`maintenance reanalyze-templates`: ключ профиля включает версии анализатора, контрактов, скилла и шрифтов) — задания уходят в очередь воркера анализа, выкладка их не ждёт; без этого генерация на старом профиле падала бы при проверке контракта. То же делает откат. Копия репозитория выпуска сохраняется в `$SERVER_DIR/releases/<тег>`; хранятся три последних выпуска, образы и копии старше удаляются.
6. Ждёт ответа `SERVER_URL` (первый сертификат занимает до минуты), затем `status: ok` в `/api/health`: база, хранилище, Valkey, воркер анализа и все воркеры генерации с пройденной проверкой рендерера. HTTP 200 с `degraded` готовностью не считается. Запросы готовности идут с самого сервера, чтобы не зависеть от VPN, прокси и DNS-кэша машины разработчика. Если адрес не ответил или health не стал `ok`, печатается хвост логов Caddy, API и воркеров.

`/api/health` показывает выложенный выпуск (`release.image_tag`, `release.commit`, `release.schema`) и итог последней сборки мусора (`gc`).

`./deploy/deploy.sh --target server --build-here` собирает образы на машине разработчика под архитектуру сервера (`docker buildx`, эмуляция для x86_64 на Apple Silicon) и передаёт их через `docker save | docker load`; образ интерфейса весит около 25 МБ, воркера — 1,4 ГБ. Нужен серверам, которым не хватает памяти на сборку Next.js. `./deploy/deploy.sh --target server --down` останавливает стек, тома (сертификаты) и данные остаются.

## Откат

```bash
./deploy/deploy.sh --target server --rollback    # или make rollback
```

Одна команда возвращает предыдущий выпуск из `deploys.log`: его образы (они остаются на сервере для трёх последних выпусков) и compose-файлы из `releases/<тег>`. Если откатываемый выпуск менял схему базы, API и воркеры останавливаются, база восстанавливается из копии, снятой перед его миграцией (`--only-db`: загрузки и артефакты остаются, лишние станут сиротами для сборки мусора; очередь очищается), текущая база откладывается в `data/.previous-<время>`. Затем `up -d` и та же проверка готовности. Откат идёт на один шаг назад; повторный `--rollback` вернёт выпуск, с которого только что откатились. Первую выкладку с тегами откатить нельзя: у неё нет предыдущего выпуска с образами.

Откат на произвольный commit — выкладка нужного состояния репозитория:

```bash
git stash            # если есть незакоммиченные изменения
git checkout <commit>
./deploy/deploy.sh --target server
git checkout main && git stash pop
```

## Резервные копии

```bash
./deploy/backup.sh --target server [--label МЕТКА] [--fetch]    # make backup LABEL=… FETCH=1
./deploy/backup.sh --target server --list
```

Копия — один tar в `$SERVER_DIR/backups/backup-<время>[-метка].tar`: `meta.json` (версия схемы, выпуск, число строк и файлов), `state.sqlite3` (снимок через backup API SQLite — живая база в WAL одним файлом не копируется), `valkey.dump` (логический дамп ключей DUMP/RESTORE с TTL, без регистраций воркеров и служебных отметок), `uploads/` и `artifacts/` без временных каталогов публикации. Рядом кладётся копия `.env` сервера (`<имя>.env`, права 0600): адреса и ключи провайдера. Порядок записи — база, очередь, файлы: файлы хранилища неизменяемы и адресуются по sha256, ревизии публикуются атомарно, поэтому копия согласована для всего, на что ссылается снимок базы; появившееся после снимка — лишние сироты, их снимет сборка мусора. Копия делается на живом стеке без остановки. Хранятся `backup.keep` последних копий из `config/app.yaml` (7), старые удаляются. Материалы организаторов и кэши в копию не входят. `--fetch` скачивает архив и `.env` в `backups/` на машине разработчика — так копия переезжает на новый сервер.

Копия перед миграцией создаётся автоматически при выкладке с изменением схемы.

## Восстановление

```bash
./deploy/restore.sh --target server --verify-only [--archive ИМЯ]      # make restore-verify
./deploy/restore.sh --target server [--archive ИМЯ|ПУТЬ] [--only-db] [--valkey restore|flush|keep]
```

`--verify-only` распаковывает копию в `backups/.verify/<имя>` — отдельный каталог, живые данные не трогаются — и сверяет: `PRAGMA integrity_check`, версию схемы (не новее кода), число строк с `meta.json`, наличие и sha256 каждого файла хранилища, на который ссылаются файлы проектов и шаблоны, манифест каждой ревизии и размер с sha256 каждого артефакта из манифеста, превью шаблонов. Ненулевой код — есть проблемы, они перечислены в выводе.

Без `--verify-only` скрипт останавливает API и воркеры, проверяет копию на staging-каталогах (при проблемах отменяет восстановление), откладывает текущие `state.sqlite3`, `uploads/` в `data/.previous-<время>` и `artifacts/{jobs,templates,packages}` в `artifacts/.previous-<время>`, переносит восстановленные на место, восстанавливает очередь (`--valkey restore`, по умолчанию; `flush` — очистить, `keep` — не трогать), поднимает стек и ждёт `status: ok`. Отложенные каталоги `.previous-*` ничего не удаляет автоматически — их убирает администратор после проверки. Задания, которые в момент копии выполнялись, после восстановления помечает ошибкой сверка (`worker_lost`), их можно повторить из интерфейса. Локальный файл в `--archive` сначала загружается на сервер (вместе с `.env`-копией, если лежит рядом).

Локальный стек: те же команды с `--target local`, копии в `backups/` репозитория.

## Сборка мусора

Хранилище и артефакты чистятся периодической задачей воркера анализа: раз в `retention.gc_interval_s` (час) API ставит задачу `gc` в очередь `analysis`. Живым считается всё, до чего можно дойти от проектов: задание, шаблон и пакет проекта, карточки ленты, файлы проекта, а от них — пакеты и шаблоны генераций, дочерние исправления, файлы пакетов и байты в хранилище; шаблоны — библиотека сервиса, они живут, пока их не удалили из библиотеки явно (`DELETE /api/templates/{id}`: строка и миниатюры сразу, задание анализа и байты — по сроку); незавершённые задания тоже живые. Остальное — сироты: задания и пакеты удалённых проектов с их артефактами, строки файлов вне проектов, байты без ссылок, каталоги без строк в базе, обрывки загрузок. Сирота при первой встрече получает отметку в таблице `gc_marks` и удаляется, только когда отметка старше срока из `config/app.yaml` (`retention.orphan_jobs_hours`, `unreferenced_uploads_hours` — сутки; `upload_tmp_hours` — 6 часов): так грация защищает промежуточные состояния (файл уже сохранён, но ещё не привязан; задание создано, но проект ещё не обновлён). Если объект снова стал живым, отметка снимается. Каждое удаление пишется в лог воркера анализа с размером; сводка — в `runs/gc/last.json` и в `/api/health` (`gc`).

Вручную (внутри контейнера API, на сервере из каталога репозитория с `.env` сервера):

```bash
docker compose -f docker/compose.yaml -f docker/compose.prod.yaml --env-file ../.env \
  run --rm --no-deps -T api python -m presentation_designer.cli.maintenance gc --dry-run
# … gc                  — обычный проход с отметками и сроками из конфига
# … gc --grace-hours 0  — удалить уже отмеченных сирот, не дожидаясь срока
```

## Проверка после выкладки

- `curl --fail "$SERVER_URL/api/health"` — `status: ok`, воркеры `analysis ≥ 1`, `generation ≥ 1`, `renderer_ok: true`, `release.image_tag` равен тегу выкладки; `degraded` означает, что часть воркеров ещё стартует или не прошла проверку рендерера, `down` — недоступны база или хранилище. Поле `provider` — сводка провайдера моделей без секретов: имя, хост, модели по ролям, `configured` (ключ и адрес заданы), `probed` (возможности записаны зондом); на готовность не влияет.
- Анализ шаблона на сервере: `execution_mode.layers["parsing.template"]` в `/api/health` равен `real` (режим `mixed`, остальные слои — заглушки); загрузка PPTX через интерфейс даёт профиль с настоящими миниатюрами слайдов за 15–60 с. Тот же анализ из контейнера воркера: `… run --rm --no-deps -T worker-analysis python -m presentation_designer.cli analyze /app/data/organizers/<файл>.pptx --out /app/runs/analyze/<имя>` (материалы организаторов на сервере — в `data/organizers`, если скопированы).
- Импорт содержания, бриф и смысловой план: слои `parsing.content`, `brief` и `generation.story` в `execution_mode` равны `real`. `curl -s "$SERVER_URL/api/brief" -H 'content-type: application/json' -d '{"text":"Сделай презентацию про запуск сервиса для руководителей, чтобы одобрили пилот, 10–12 слайдов"}'` возвращает `source: model` и модель в поле `model` (при недоступном провайдере — `source: heuristic`, диалог не ждёт); в интерфейсе карточка «понял задачу так» показывает, чем выделены поля. Импорт материалов через интерфейс даёт пакет с блоками, фактами с контекстом, наборами данных и изображениями (`GET /api/content/{id}`, картинки — `…/assets/<путь>`); генерация строит StoryPlan моделью (`GET /api/generations/{job}/story`, `generation_meta.models`, `coverage`), повтор с теми же содержанием и настройками переиспользует план (`metrics.cache.story_hit`). Из контейнера воркера: `… run --rm --no-deps -T worker-generation python -m presentation_designer.cli import /app/examples/content --out /app/runs/import` и `… story /app/runs/import/package.json --out /app/runs/import/story.json`.
- Вёрстка: слой `layout` в `execution_mode` равен `real`; генерация через интерфейс даёт три PPTX, собранных из образцов загруженного шаблона (`GET /api/generations/{job}/artifacts/<variant>/r1/deck.pptx` открывается python-pptx и PowerPoint, число слайдов по плану, текст плана в слайдах, таблицы и диаграммы нативные), рядом `composed.json` (ComposedDeck) и `plan.json`. Из контейнера воркера: `… run --rm --no-deps -T worker-generation python -m presentation_designer.cli compose /app/runs/plan/balanced.json --profile /app/runs/analyze/profile.json --template /app/tests/fixtures/pptx/mini_template.pptx --content /app/runs/import/package.json --out /app/runs/compose/balanced --pdf` (с `--pdf` — PDF через LibreOffice образа для проверки вида).
- Реальный вызов модели из контейнера воркера (адаптер, лимитер в Valkey, ключ из `.env` сервера):

  ```bash
  cd /srv/presentation-designer/repo
  docker compose -f docker/compose.yaml -f docker/compose.prod.yaml --env-file ../.env \
    run --rm --no-deps -T worker-generation python -m presentation_designer.llm.probe smoke
  # полный зонд с отчётом: … python -m presentation_designer.llm.probe probe --report /app/runs/llm-capabilities.md
  # лимитер из нескольких процессов: … python -m presentation_designer.llm.probe limiter --processes 4
  ```

  Ответ — одна строка JSON: `ok`, модель, задержка, usage, `limiter: valkey`. Без настроенного провайдера команда завершается сообщением «провайдер не настроен» и кодом 1. Внутри контейнера `PD_VALKEY_URL` указывает на Valkey стека, поэтому smoke проходит через тот же общий лимитер, что и воркеры; `--no-deps` не поднимает лишних контейнеров, а Valkey уже работает.
- `make test-server` — интеграционные тесты API (`tests/integration`, `API_BASE_URL`) и 27 сквозных тестов интерфейса в трёх движках против `SERVER_URL` из `deploy/server.env`; без файла — против локального стека. Тесты удаляют созданные ими проекты, на сервере после прогона тестовых проектов не остаётся (артефакты их заданий снимает сборка мусора по сроку).
- Сценарий в браузере по адресу сервера: главная → новый проект → шаблон и материалы в чат → бриф → генерация → три варианта → аудит → исправление → скачивание PPTX/PDF/HTML; проект открывается по ссылке из другого браузера.
- Перезапуск: `docker compose … restart` и повторное открытие проекта — проекты, файлы, задания и артефакты восстанавливаются из `data/` и `artifacts/`. Упавший контейнер поднимает политика `unless-stopped` (проверено убийством процесса воркера: контейнер возвращается за секунды, воркер снимает регистрацию прежнего процесса и заново проверяет рендерер); у воркеров есть healthcheck (регистрация в Valkey жива), у API — `/api/health`. После пересоздания контейнеров или аварии `workers` в health может до 90 секунд (`queue.heartbeat_ttl_s`) считать и прежние регистрации.
- Замер холодного запуска: `make cold-start MODE=down-up` и `MODE=restart` (`scripts/measure_cold_start.sh`), результаты в `docs/evaluation.md`.

## Логи и перезапуск

Команды на сервере из каталога репозитория (`$SERVER_DIR/repo`), с `.env` сервера и обоими файлами Compose:

```bash
cd /srv/presentation-designer/repo
C="docker compose -f docker/compose.yaml -f docker/compose.prod.yaml --env-file ../.env"
$C ps
$C logs --tail=100 api
$C logs -f worker-generation
$C logs --tail=100 worker-analysis      # здесь же сборка мусора: что удалено и сколько освобождено
$C logs --tail=100 caddy
$C restart api
```

Логи контейнеров — json-file с ротацией (20 МБ × 5 на сервис). Задания без живого исполнителя (потерянный воркер, истёкший срок) API помечает ошибкой при периодической сверке (`queue.reconcile_interval_s`); состояние заданий читается из SQLite, а не из очереди.

Журнал выпусков: `$SERVER_DIR/deploys.log` — время, действие (`deploy`/`rollback`), тег, предыдущий тег, commit, признак незакоммиченных изменений, ветка, версия схемы до и после, копия перед миграцией, адрес. Сертификаты Caddy лежат в томе `presentation-designer_caddy_data`; при `down` и повторном `up` они не запрашиваются заново.

## Переезд на другой сервер

Сценарий проверяемый, но второй машины для прогона пока нет: **ожидает проверки** (чек-лист этапа 3 в плане). Прогон на том же сервере переезд не заменяет.

1. На старом сервере: `./deploy/backup.sh --target server --label move --fetch` — копия и `.env` скачиваются в `backups/` на машине разработчика.
2. Новый `deploy/server.env`: `SERVER_SSH` новой машины, тот же `SERVER_DIR`, `SERVER_URL` — прежний домен (после переключения A-записи) или временно `https://<ip>.sslip.io`.
3. `./deploy/install.sh --target server` — Docker, пользователь, каталоги, `.env` с умолчаниями. Ключи провайдера — из скачанной копии `.env` (вписать вручную в `$SERVER_DIR/.env`).
4. `./deploy/deploy.sh --target server` — образы собираются, стек поднимается с пустой базой текущей схемы.
5. `./deploy/restore.sh --target server --archive backups/backup-…-move.tar` — архив загружается на сервер, стек останавливается, данные восстанавливаются, стек поднимается; проверить, что проект из копии открывается по ссылке.
6. `scp -r data/organizers …` — материалы организаторов, если нужны для прогонов.
7. Смена адреса — только `SERVER_URL` в `deploy/server.env` и следующая выкладка: адрес не зашит ни в образы, ни в данные (интерфейс обращается к API того же origin, Caddy читает имя из `.env`). Код и образы не меняются.

## Локальный запуск того же стека

`make up` (то же, что `./deploy/deploy.sh --target local`) собирает и поднимает базовый compose на этой машине по адресу `http://localhost:8080` с настройками из корневого `.env` (создаётся из `config/.env.example`); прод-надстройка с лимитами локально не применяется. Каталог данных со SQLite локально живёт на томе Docker `app_data`: WAL SQLite требует разделяемой памяти, которой нет у bind-mount Docker Desktop. `make down` останавливает контейнеры. Если путь к репозиторию содержит не-ASCII символы, сборка идёт через символическую ссылку в `$TMPDIR` — BuildKit в Docker 29 иначе отказывается. Без Docker: `make api` поднимает API со встроенным исполнителем задач, `make dev-real` — интерфейс с прокси `/api`. Локальный запуск служит отладке и серверную проверку этапа не заменяет.
