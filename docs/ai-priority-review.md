# Приоритет: качество ИИ, а не собственный офисный движок

## Решение после проверки текущего кода и артефактов

Серверная генерация StoryPlan/SlidePlan, контекстный чат и точечная правка PPTX
уже реализованы. Это не означает готового качества продукта. Развитие precision SDK
не должно быть предварительным условием для проверки генерации на неизменяемых копиях.
ONLYOFFICE остаётся средством просмотра/ручного редактирования и конвертации;
переход на другой редактор и интеграция официального AI-плагина сейчас не нужны.

Сохранность ручных правок, проверка базовой ревизии и запрет перезаписи активной
сессии остаются обязательными. ИИ работает с актуальной сохранённой ревизией,
а не пересобирает старый план поверх ручных изменений. Неослабленный аудит
precision и production-барьеры из `office-save-fixes.md` сохраняются.

## Ближайшая работа и критерий остановки

1. Довести одну колоду (Education balanced) на фиксированных материалах:
   тезисы/числа/единицы сохранены, число карточек соответствует содержанию,
   нет оторванных подписей, повторов, нечитаемого KPI и переполнений.
   Сравнивать исходные материалы → план → PPTX → PDF, а не только статус job.
2. Добавить проверку ИИ-сокращений на сохранение числа **вместе с единицей и периодом**.
   Неполный ответ не публиковать молча: повтор или объяснимый отказ, без бесконечных
   попыток. Точечная правка — не замена проверки качества генерации целой колоды.
3. После доказанного улучшения одного сценария повторить его на Tech/Workspace/ЛЦТ;
   отдельно проверить UI: бриф → генерация → просмотр → ИИ-правка → новая ревизия.
4. Precision: cache-safe обновление, новый UI-acceptance и memory soak остаются
   отдельными условиями production, не блокируют пункты 1–2. Потеря пользовательских
   правок по-прежнему блокирует выпуск редактирования.

Не добавлять параллельно новый редактор, plugin-мост, потоковую вставку слайдов
и новую систему генерации. Использовать уже существующие backend, очередь и модели.

### Реализация

- Числовая проверка теперь сравнивает также целые DrawingML-абзацы **реальной
  исходной ревизии** с результатом всех patches. Соседние неизменённые runs входят
  в контекст; пробелы не вставляются искусственно, `a:br` трактуется как перенос.
  Так нельзя удалить `в день` или единицу из отдельного run и нельзя перенести
  период в другой абзац. Проверка каждого run тоже сохранена; перенос чисел между
  runs намеренно остаётся запрещённым. XML-структура не меняется.
- Проверяются поддерживаемые диапазоны, проценты, цифровые даты, суммы с группами
  тысяч и множителями/валютами. Это консервативное сопоставление выражений, а не
  семантическая гарантия: неизвестные единицы, числа словами, календарные сроки
  вроде «к декабрю», отрицания и факты через границы абзацев пока не покрыты.
- Повторы/отказы для трёх путей (колода, объект, несколько объектов) проверяются
  через настоящий LLM-клиент со stub transport, включая число/единицу/период
  в разных runs. Проверяется строгая сохранность оформления и остальных частей.
- Seed-скрипт теперь допускает `--source --project`: создаёт новый sandbox-проект
  с точной копией PPTX и правильным количеством слайдов. Уникальность копий и
  неизменность исходника покрыты тестами; пользовательские ревизии не используются.

### RQ: воспроизведён механизм, исправление ещё не внесено

`check_rq.py`, `rq-report.json`, `rq.exit=0`: отдельные временные Docker network,
Valkey и RQ 2.12.0 worker без рабочих данных, API-ключей, портов или mounts.
После эксперимента все временные контейнеры и сеть удалены.

1. `worker_ttl=90`, обычный idle 160 секунд: `queues=[sandbox]`, регистрация полная.
2. Пауза только тестового воркера 160 секунд (ключ успел истечь), затем resume:
   `Worker.all()` возвращает процесс с `queues=[]`; hash содержит **только
   `last_heartbeat`**, TTL снова продлён. `Worker.heartbeat()` делает HSET одного
   поля и EXPIRE, но не восстанавливает birth/queues/hostname и прочую регистрацию.
3. Перезапуск только тестового Valkey без persistence: `Worker.all()=[]`, процесс
   worker по-прежнему Running. Наличие живого процесса не означает готовность RQ.

Это воспроизводит прежний симптом и указывает на уязвимость к паузе VM/истечению
регистрации и утрате Redis-состояния; причина **конкретного прошлого инцидента**
этим не доказана. Текущий `healthcheck()` проверяет только имя из `Worker.all()`:
неполная запись с hostname в имени может ошибочно считаться healthy. Нужны отдельные
регрессии на восстановление полной регистрации и проверку ожидаемых очередей;
простое повторение рестартов не является исправлением. Рабочий Valkey не трогался.
