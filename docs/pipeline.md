# Конвейер по слоям: команды и устройство

Подробности к разделу «Команды по слоям» из [README](../README.md): что делает каждый слой, какой командой его запустить отдельно и какие у него правила. Границы слоёв и граф заданий — в [ARCHITECTURE.md](../ARCHITECTURE.md).

## Проверка движка PPTX и рендера

```bash
uv run scripts/inspect_pptx.py data/organizers/*.pptx --json runs/pptx-probe/inspect.json
uv run scripts/probe_pptx.py --templates-dir data/organizers --out runs/pptx-probe --report docs/pptx-capabilities.md
```

`probe_pptx.py` проверяет на каждом шаблоне сохранение без изменений, клонирование образцов, замену текста, нативные таблицу и диаграмму, независимость копий диаграммы и удаление образцов, затем рендерит результаты в PDF и миниатюры (нужен ONLYOFFICE; без него `--skip-render`). Тот же скрипт запускается в образе воркера (`docker compose run --rm worker-generation …`), результаты по машинам собираются в `docs/pptx-capabilities.md`. Открытие файлов в PowerPoint остаётся ручной проверкой по чек-листу из того же документа.

## Анализ шаблона

```bash
uv run -m presentation_designer.cli analyze "data/organizers/VK Tech шаблон.pptx" --out runs/analyze/vktech
# --no-render без ONLYOFFICE, --no-vlm только эвристики, --report сводка в stderr
```

Анализатор (`src/presentation_designer/parsing/template`) читает пакет, разделяет слайды на образцы содержания, инструкции и каталоги иконок, строит палитру, шрифты и шкалу кеглей с областью действия, находит постоянные элементы и ресурсы, превращает образцы в композиционные паттерны со слотами (ёмкость по метрикам шрифтов рендерера) и правилами из текста шаблона, объединяет образцы одной сигнатуры в группы взаимозаменяемых (`group_id`) и определяет тон фона каждого образца (`tone`: заливка слайда, закрывающая картинка, фон макета, мастера или тема) и стиль `style_key` «тон|семейство макета|plain»; миниатюры — ONLYOFFICE → PDF → PNG под слотом рендера, роли образцов уточняет VLM по представителям групп. Тот же анализ выполняет воркер при `POST /api/templates`; результаты на четырёх шаблонах — [docs/template-analysis.md](template-analysis.md).

## Импорт содержания и смысловой план

```bash
uv run -m presentation_designer.cli import examples/content/ --out runs/import/
# --no-model без уточнения контекста фактов моделью, --no-cache перечитать файлы, --report сводка
uv run -m presentation_designer.cli story runs/import/package.json --out runs/import/story.json
# --settings settings.json явные настройки запроса (language, slide_count, seed), --no-model черновик без модели
```

Импортёр (`src/presentation_designer/parsing/content`) разбирает docx, xlsx и csv, pdf с текстовым слоем, markdown и txt, pptx как материал (текст слайдов и заметок, таблицы, данные диаграмм, картинки) и изображения в общую модель блоков, кэширует разбор каждого файла по sha256 и версии парсера (`data/import-cache`: смена брифа или удаление одного материала не перечитывает остальные), собирает реестр фактов с контекстом (показатель, период, субъект, единица, сравнение, исходный фрагмент или ячейка), производные показатели с формулой и наборы данных с типами колонок; неоднозначный контекст фактов уточняет модель (скилл `content_importer`) со ссылкой на фрагмент, значения она не переписывает. Бриф из сообщения чата извлекает скилл `brief_extractor` (без рассуждения, тайм-аут `timeouts.brief_s`), при недоступности модели — те же правила, что в интерфейсе, с `source: heuristic`. Смысловой план StoryPlan (`src/presentation_designer/generation/story.py`, скилл `story_planner`) строится один раз на содержание и эффективный бриф: тезисы ссылаются на блоки, факты, наборы данных и изображения, покрытие обязательных фактов и пунктов брифа проверяет код; кэш плана — по `content_hash`, а не по идентификаторам заданий. Собственный контент-пакет для проб — `examples/content/`.

## Планы трёх вариантов

```bash
uv run -m presentation_designer.cli plan runs/import/story.json runs/analyze/profile.json \
    --content runs/import/package.json --variants compact,balanced,detailed --out runs/plan/
# --no-model детерминированный черновик, --no-cache без кэша готовых планов, --report сводка
```

Планировщик (`src/presentation_designer/generation/variants.py`, скилл `variant_planner`) строит из общего StoryPlan и профиля шаблона по одному SlidePlan на вариант оси плотности: титульный, разделители, оглавление и финальный слайд подбираются кодом из всего пула роли — внутри колоды одним стилем (`style_key`), а у compact/balanced/detailed разными (`plan.style_policy: per_variant`; `first` — первый паттерн пула у всех), титул и финал в тон разделителя; серии одинаковых композиций разбавляются сначала братьями по группе образцов, затем другими кандидатами; содержательные тезисы делятся на пакеты по разделам, для каждого тезиса код отбирает кандидатов-композиций по подаче, вместимости и поддерживаемой визуализации (`matching.py`: таблица только при слоте таблицы, диаграмма — при слоте диаграммы или картинке диаграммы в образце), а модель получает пакет тезисов с фактами, короткий список композиций с ёмкостью и правила варианта и выбирает группировку и формулировки, ссылаясь на факты через `{fact:<id>}`; пакеты идут параллельно под общим deadline, негодный пакет повторяется с подсказкой отдельно. Слоты, подстановку фактов и измерение по файлам шрифтов рендерера выполняет код (`capacity.py`): при переполнении — более вместительная композиция, кегль из шкалы шаблона, сокращение без потери фактов, разделение слайда в пределах диапазона; невозможность разместить обязательное при точном числе слайдов — структурированная ошибка, а не тихая потеря. Планы проверяются валидаторами связей (слоты, факты, число слайдов, покрытие тезисов), сравниваются по последовательности композиций и визуализации — содержательных слайдов отдельно, чтобы разные разделители не маскировали одинаковое содержание (пары без различий записываются предупреждением `variants_indistinct`); разнообразие колоды измеряет `scripts/deck_diversity.py` по планам и ComposedDeck (доля самой частой композиции, серии, стили разделителей, иконки из плана, расстояние между вариантами; строки «до/после» в [docs/evaluation.md](evaluation.md)) и кэшируются в `data/plan-cache` по StoryPlan, структуре и ёмкости паттернов, метрикам шрифтов, настройкам и версиям скилла.

## Вёрстка PPTX

```bash
uv run -m presentation_designer.cli compose runs/plan/balanced.json --profile runs/analyze/profile.json \
    --template tests/fixtures/pptx/mini_template.pptx --content runs/import/package.json --out runs/compose/balanced/
# --prune-layouts убрать неиспользуемые макеты, --pdf ещё и PDF через ONLYOFFICE, --report отчёт
```

Композер (`src/presentation_designer/layout/compose.py`) берёт исходный PPTX как основу: для каждого слайда плана клонирует образец паттерна с графом связей (макет общий, картинки разделяются, диаграммы с книгами данных копируются), заполняет слоты по `element_ref` — текст с сохранением оформления абзацев и фрагментов и явным кеглем из `fit.size_pt`, факты значениями как в источнике, списки абзацами по маркированному абзацу образца, таблицы по строкам-шаблонам таблицы образца, нативные диаграммы (в слоте chart — данные в диаграмму образца, вместо картинки диаграммы — новая на её месте; так же и с диаграммой, нарисованной руками: ряд столбиков из картинок распознаётся анализатором целиком — `parsing/template/drawn_charts.py` — становится одним слотом chart, а его части перечислены в `chart_parts` паттерна и убираются, когда диаграмма построена; зрение модели тут отвечает только на вопрос «график ли это»: если VLM ставит образцу роль chart, а строгие пороги ряда не сошлись, поиск повторяется мягкими — объекты и область всё равно находит код, поэтому без модели разбор работает так же), схемы из фигур, картинки пакета с crop, иконки шаблона с перекраской масок; незаполненные карточки убираются по `removable_object_ids` вместе с пустыми рамками, статика и логотипы остаются, крошечные слоты (номера шагов) сохраняют текст образца. Образцы удаляются, номера слайдов пересчитываются, пакет проверяется (`layout/integrity.py`), по сохранённому файлу строится ComposedDeck (`layout/composed.py`: объекты, геометрия, вычисленные стили, ресурсы, связь со слотами и блоками, `content_source` у каждого объекта). Требование сохранности профиля: `template_hash` профиля должен совпадать с файлом шаблона.

## ИИ-правки: открытый PPTX и план генерации

В интерфейсе проекта команда `/edit` запускает точечную правку текста офисной копии с проверкой базовой ревизии. Изображения и структуру презентации редактируют в ONLYOFFICE; вложения к команде `/edit` не поддерживаются. Это отдельный путь от правки плана генерации через CLI/API ниже.

```bash
uv run -m presentation_designer.cli edit-slide runs/plan/balanced.json --story runs/import/story.json \
    --profile runs/analyze/profile.json --content runs/import/package.json \
    --slide 5 --instruction "сделай заголовок короче и вынеси 40 % в показатель" --out runs/edit/
# затем compose по runs/edit/plan.json; --report сводка (композиция до/после, переполнения, отказ)
```

API `POST /api/generations/{job}/variants/{variant}/edits` создаёт новую ревизию одного варианта по инструкции к одному слайду. Слой `generation/edit.py` (скилл `slide_editor`) получает план, композицию, соседние слайды, факты и доступные варианты подачи. Новый план проходит сборку слотов, проверку ёмкости и связей, затем compose → export → audit. Факты передаются ссылками `{fact:<id>}`; запрос вне доступных данных или за пределами одного слайда отклоняется с причиной. Этот механизм не синхронизирован с ручными изменениями офисной копии и не является обработчиком обычных вопросов чата.

## Правки объектов через CLI/API

Основной визуальный редактор проекта — ONLYOFFICE. Описанный ниже `slide_patch` — отдельный механизм правок плана генерации; офисные изменения не записываются в `slides[].overrides` и не воспроизводятся пересборкой этого плана.

```bash
uv run -m presentation_designer.cli patch-slides runs/compose/balanced/plan.json --patch runs/patch/patch.json \
    --profile runs/analyze/profile.json --content runs/import/package.json \
    --deck runs/compose/balanced/composed.json --out runs/patch/
# затем compose по runs/patch/plan.json (для правок с источником file — с --uploads data/uploads)
```

Ручные правки объектов готового слайда: текст, кегль, начертание, цвет и выравнивание, положение и размер (в том числе внутри групп), замена картинки или иконки из ресурсов шаблона, материалов пакета или своего файла с перекраской монохромных иконок, удаление объекта (клавиша Delete или кнопка в панели), своя надпись на слайде (кнопка «Текст»), фон слайда (цвет, картинка, «как в макете») и перестановка слайдов. Правки хранятся в плане варианта как `slides[].overrides` и применяются композером после заполнения слота (`src/presentation_designer/layout/overrides.py`), поэтому ревизия воспроизводится из плана, а правка из чата сбрасывает ручные правки только у переделанного слайда (`overrides_dropped`). Документ `slide_patch` (`contracts/schemas/slide_patch.schema.json`) уходит в `POST /api/generations/{job}/variants/{variant}/patches` и создаёт новую ревизию без модели тем же путём, что правка из чата; `edits[]` результата помечает такие правки `origin: editor`. Адрес объекта — `object_id` из ComposedDeck базовой ревизии с охраной `source_object_id`/`slot_id`: несовпадение — правка отброшена с предупреждением. Своя надпись (`op: add_text`) адресуется придуманным редактором `usr_…`: объекта с таким адресом в базовой ревизии нет, номер готовой фигуры выводится из него детерминированно, поэтому пересборка ревизии из плана повторяема, а правки текста и положения той же надписи в том же патче находят её по придуманному адресу. Значения вне токенов шаблона применяются с предупреждением `override_off_template`, текст, не помещающийся после правки, — `override_overflow`. Медиа колоды лежит рядом с ревизией (`media/`, `assets[].artifact`), ресурсы шаблона отдаёт `GET /api/templates/{id}/media/{asset_id}`, а для подложки холста анализ рендерит пустой слайд каждого макета (`previews/layout-<id>.png`).

## Вызовы моделей

```bash
make llm-smoke          # один реальный вызов модели: ключ и адрес из .env
make llm-probe          # зонд провайдера с отчётом в docs/llm-capabilities.md
make llm-limiter-check  # лимитер из нескольких процессов против Valkey
```

Все вызовы моделей идут через пакет `src/presentation_designer/llm`: клиент на openai SDK с `base_url` провайдера, роли `llm`/`vlm` из `config/models.yaml`, общий для всех воркеров лимитер одновременности, RPM и TPM в Valkey, свои повторы (429, сеть, 5xx, негодный ответ) в пределах deadline, кэш ответов в `data/llm-cache`, записанные ответы для тестов (`tests/fixtures/llm`, режимы `record`/`replay`) и учёт usage по этапам. Скиллы — `skills/<name>/skill.yaml` с версионируемыми промптами; версия промпта входит в ключ кэша и в результат. Возможности endpoint (model ID, JSON-схема, изображения, streaming, рассуждение, одновременность) измеряет зонд, результат — [docs/llm-capabilities.md](llm-capabilities.md); до зонда слои конвейера работают в режиме заглушек.

## Отладка заданий

```bash
uv run python tools/job_doctor.py                  # сверка артефактов всех заданий между собой
uv run python tools/job_doctor.py job_ab12… -v     # одно задание, построчная сверка текста слайдов
uv run python tools/ui_doctor.py prj_ab12…         # интерфейс вживую: тот ли слайд и те ли рамки
```

Слайд доходит до пользователя тремя путями: миниатюра и PDF от рендерера, `composed.json` для
редактора и рамок аудита, `deck.pptx` для скачивания. Если они разойдутся, интерфейс покажет
один слайд, а править и проверять будет другой. `job_doctor` сверяет состав файлов, число
слайдов, порядок (по тексту слайдов из pptx и текстового слоя PDF), нумерацию в описании,
ссылки находок на слайды и объекты и рамки в пределах холста. `ui_doctor` водит настоящий
Chrome по ленте миниатюр и сверяет нарисованные рамки с `audit.json`, включая перестановку
слайдов в черновике редактора. Оба возвращают код 1 при расхождении и годятся для CI.

## Не сделано: AI-плагин ONLYOFFICE

Официальный AI-плагин ONLYOFFICE в проекте не используется. У ONLYOFFICE есть AI-плагин с поддержкой презентаций, но в нашей конфигурации плагины отключены (`customization.plugins: false`). Текущие контекстный чат и `/edit` реализованы нашим приложением, а не этим плагином.

Что проверить в отдельном прототипе:

- Совместимость AI-плагина с установленной ONLYOFFICE Docs Community **9.3.1** и фактически доступные действия над презентацией.
- Подключение нашего провайдера моделей без раскрытия серверных секретов в браузере.
- Возможность передачи контекста проекта: брифа, материалов, шаблона и результатов аудита. Простое включение плагина этот контекст не подключает.
- Совместимость правок плагина с сохранением, офисными ревизиями и нашим `/edit`; сохранность ручных изменений после повторного открытия PPTX.

Результат эксперимента — зафиксировать работающие сценарии и ограничения и решить, подключать ли AI-раздел как дополнительный инструмент или оставить отдельный чат. Плагин не заменяет серверную очередь генерации и аудит. Прототип моста для потоковой вставки слайдов — **другая задача**, не готовая возможность штатного AI-раздела; подробнее в [документе по оркестрации](onlyoffice-orchestration.md).
