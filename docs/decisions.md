# Архитектурные решения

Короткие записи о принятых решениях. Каждая новая зависимость и каждое отклонение от FRAMEWORKS.md получают запись здесь.

## 2026-09-15. Стек

Next.js с TypeScript и App Router, Mantine, FastAPI и Pydantic, python-pptx с lxml, LibreOffice и pypdfium2, openai SDK, RQ и Valkey, SQLite, Docker Compose на сервере Ubuntu. Модели только через API провайдера Qwen; в топ-10 инференс VK с Qwen 3.8 27B. Основание: ТЗ VK Tech и сравнение технологий командой.

## 2026-09-15. Лицензия проекта

Apache-2.0. Совместима со всем стеком и с требованием ТЗ к моделям (Apache 2.0 или MIT). Выбор по умолчанию из плана; может быть заменена на MIT по решению команды до публикации.

## 2026-09-15. Общий смысловой план StoryPlan

Содержание формируется один раз из ContentPackage, три варианта меняют композицию и визуализацию, но обязаны покрыть все обязательные тезисы. Снижает повторную генерацию содержания и даёт единую точку проверки фактов. Контракт `story_plan` версии 1.1.

## 2026-09-15. ComposedDeck

После вёрстки строится описание фактического файла: объекты, вычисленные стили, геометрия, порядок слоёв, ресурсы, связи со слотами плана. Его используют аудит, подсветка находок и HTML-экспорт; SlidePlan для этого недостаточен, он не знает оформления клонированного слайда. Контракт `composed_deck` версии 1.1.

## 2026-09-15. Общий лимитер запросов к провайдеру в Valkey

Квота провайдера одна на все воркеры, варианты и аудит, поэтому ограничитель распределённый, а не на процесс. Ожидание квоты измеряется и попадает в метрики задания.

## 2026-09-15. Роли воркеров

Отдельные сервисы Compose для очередей `analysis` и `generation`: три воркера генерации и один воркер анализа и исправлений. Масштабирование одной реплики до четырёх не резервирует воркер под анализ, поэтому роли разделены сервисами.

## 2026-09-15. Контракты версии 1.1

Все документы получили `schema_version` 1.1. Новые схемы: `story_plan`, `composed_deck`, `job_status`. Общие определения вынесены в `common`: ревизия, размер слайда, состояния задания, этапы, режим исполнения слоёв, вычисленные стили с источником. Примеры версии 1.0 не поддерживаются: смешение версий запрещено. Поля, которые станут ясны при реализации слоёв, добавляются версией 1.2 на этапах 6 и 8.

## 2026-09-15. Генерация моделей из объединённой схемы

datamodel-code-generator не разрешает ссылки между файлами при генерации из каталога с `--use-title-as-name`, поэтому `scripts/gen_contracts.py` собирает все схемы в один документ с `$defs` и переписывает ссылки. Тест `test_generated_models_have_no_drift` следит, что `models.py` соответствует схемам.

## 2026-09-15. pnpm без corepack

corepack не установился на машине разработчика без прав администратора; pnpm 11 используется напрямую, поле `packageManager` в `frontend/package.json` сохранено для corepack на сервере и в CI.

## 2026-09-15. Проект как единица интерфейса, реестр в localStorage

Интерфейс организован вокруг проекта: одна презентация со своим шаблоном, содержанием, настройками и заданием генерации. Главный экран — сетка проектов, внутри — редактор с панелью разделов слева и предпросмотром справа. У HTTP API нет операции списка заданий, поэтому реестр проектов, бриф и настройки хранятся в localStorage браузера, а задания, профили и артефакты — на сервере. Список проектов на сервере (и его связь с заданиями) решается на этапе 2 вместе с API; клиентский реестр рассчитан на замену без изменения экранов.

## 2026-09-15. Визуальная система интерфейса

Тема Mantine переопределена в `frontend/lib/theme.ts`: графитовые основные действия, один приглушённый синий для выбора и ссылок, без теней, единая шкала скруглений, бейджи без капса. Шрифт Golos Text (пакет `@fontsource-variable/golos-text`, Apache-подобная лицензия OFL) поставляется с приложением: полноценная кириллица и никаких запросов к внешним шрифтовым сервисам при сборке и в работе. В узких панелях вложенные карточки заменены секциями с разделителями, чтобы интерфейс не спорил с оформлением презентации.

## 2026-09-15. Чат как оркестратор конвейера в интерфейсе

Редактор проекта построен вокруг чата: пользователь бросает файлы и описывает задачу одной фразой, а не заполняет мастер из форм. Файлы распознаются по расширению без модели (PPTX уточняется кнопкой: шаблон или материал), бриф из текста извлекает сервер (`POST /api/brief`; в режиме заглушек — эвристика в MSW), настройки генерации скрыты за «Изменить» и берут умолчания из ТЗ. Каждый шаг конвейера появляется в чате сообщением ассистента, которое читает живое состояние проекта и сервера по идентификаторам (см. запись от 21.09), поэтому эксперты видят слои по порядку, а запрос генерации остаётся явным и воспроизводимым. Под капотом те же операции API; чат ничего не решает сам, кроме порядка вызовов.

## 2026-09-15. Caddy как вход стека

Один внешний сервис: TLS с автоматическим сертификатом (домен или `<ip>.sslip.io`), сжатие, лимит тела запроса и маршрутизация к интерфейсу, а с этапа API — к `api`. Лицензия Apache-2.0. Альтернатива nginx с certbot требует отдельного цикла продления сертификатов и второго конфига. На время обработки не влияет: тяжёлая работа идёт в воркерах.

## 2026-09-15. Интерфейс как отдельный сервис Compose

Статический экспорт Next.js собирается в образ `presentation-designer/frontend` (многоступенчатая сборка: Node 22 → Caddy как файловый сервер) и отдаётся входному Caddy по внутреннему адресу `frontend:8080`. Режим API фиксируется аргументом сборки; сейчас `mock`. На этапе API решается, остаётся ли интерфейс отдельным сервисом или входит в образ API, как записано в плане; входной Caddyfile в обоих случаях меняется только маршрутом `/api/*`.

## 2026-09-15. Синхронизация репозитория на сервер по списку git

`deploy.sh` отправляет на сервер файлы из `git ls-files --cached --others --exclude-standard` архивом через SSH и заменяет каталог `repo` целиком. Так на сервер не попадают `.git`, локальные планы, материалы организаторов и `.env`, а удалённые в репозитории файлы не остаются на сервере. Образы собираются на сервере; для слабых машин есть `--build-here` со сборкой под архитектуру сервера и передачей через `docker save`/`docker load`.

## 2026-09-15. Состояние остаётся в SQLite

Рассмотрен переход на PostgreSQL. Отклонён: сервис работает на одном сервере, писателей мало (API и четыре воркера, несколько строк на задание), база хранит только метаданные, файлы лежат отдельно. SQLite в режиме WAL без дополнительных слоёв абстракции; резервная копия — снимком базы. Граница решения записана явно: второй сервер, несколько арендаторов или отказоустойчивость потребуют Postgres, и на этот момент в базе будут только демонстрационные данные, переносить нечего.

## 2026-09-16. Интерфейс остаётся отдельным сервисом, API за Caddy

План предполагал сборку статического экспорта в образ API. Оставлен отдельный сервис `frontend` (образ со статикой), а вход Caddy направляет `/api/*` в `api:8000`, остальное — в интерфейс. API не раздаёт статику и не нуждается в SPA-fallback, образы пересобираются независимо, один origin сохраняется. Caddyfile передаётся в контейнер как `configs`, а не bind-mount: compose пересоздаёт Caddy при изменении файла, и после замены каталога `repo` при выкладке не остаётся ссылки на старый файл.

## 2026-09-16. Один Dockerfile для API и воркера

`docker/app.Dockerfile` с целями `api` и `worker`: общая база с зависимостями по `uv.lock`, у воркера дополнительно LibreOffice 7.4, шрифты Liberation, DejaVu, Carlito и Noto. Проверка рендерера выполняется при старте воркера генерации на собственной фикстуре, результат читает `GET /api/health`. Контейнеры работают от пользователя сервиса (`PD_UID`/`PD_GID`), данные — в каталогах сервера вне репозитория.

## 2026-09-16. SQLite и локальный стек Docker Desktop

WAL SQLite требует разделяемой памяти между процессами; bind-mount Docker Desktop на macOS её не даёт, и дочерние процессы воркера падали по SIGBUS. Локально каталог данных со SQLite живёт на томе Docker (`app_data`), на сервере — в `$SERVER_DIR/data` на обычной файловой системе. Родительский процесс воркера SQLite не открывает: оркестратор строится в процессе задачи. Ещё одна особенность Docker 29: BuildKit не собирает образы из каталога с не-ASCII символами в пути, поэтому `deploy.sh --target local` работает через символическую ссылку.

## 2026-09-16. Заглушки конвейера и сценарии тестов

Заглушки возвращают документы из `contracts/examples` и настоящие файлы: PPTX через python-pptx, PDF и миниатюры через Pillow, HTML текстом; каждый этап выдерживает паузу `execution.stub_stage_delay_ms`, чтобы прогресс был виден. Для сквозных тестов имя шаблона со словом «fail» роняет вариант detailed на сборке — это единственный тестовый крючок, он описан в `pipeline/stubs.py`. Шаблоны идемпотентны по sha256, поэтому у такого сценария отдельная фикстура `mini_template_fail.pptx`.

## 2026-09-16. python-pptx утверждён движком PPTX, UNO не понадобился

Этап 0A: на трёх шаблонах VK, шаблоне ЛЦТ и собственной фикстуре проверены открытие и сохранение без изменений, клонирование слайдов с группами, обрезкой картинок и смешанными стилями, замена текста с сохранением оформления фрагментов, нативные таблица и диаграмма, две независимые копии диаграммы с отдельными книгами данных, удаление образцов. Связи пакета целы, LibreOffice рендерит копии без потерь относительно исходника. Клонирование собрано из сериализованного XML части и переноса связей (`layout/ooxml.py`), потому что публичного API у python-pptx нет; удаление опирается на то, что python-pptx сохраняет только части, достижимые от корня пакета. Резерв UNO для отдельных операций не потребовался; открытие в PowerPoint без восстановления — ручная проверка пользователя, до неё приёмка не считается полной. Замеры и ограничения: `docs/pptx-capabilities.md`.

## 2026-09-16. Подготовленный профиль LibreOffice и шрифт Play в образе воркера

Каждая конвертация запускает отдельный процесс LibreOffice с временным профилем — копией `/opt/lo-profile`, созданного при сборке образа пробной конвертацией. Так первый запуск в контейнере не тратит время на инициализацию реестра, а процессы не разделяют состояние. Шрифт Play (OFL, Google Fonts) добавлен в `docker/fonts/`: он основной в шаблонах VK, встроенные в PPTX копии LibreOffice не использует. Пул постоянно запущенных процессов через UNO не вводится: время конвертации определяется рендером страниц, а не запуском, и это записано в замерах этапа 0A. Новых зависимостей Python нет.

## 2026-09-16. Прод-надстройка Compose и пределы памяти по замерам

`docker/compose.prod.yaml` дополняет базовый `docker/compose.yaml` на сервере (оба файла через `-f`), а не заменяет его: локальный `make up` остаётся на базовом. Пределы контейнеров — из замеров этапа 0A: воркер 1,5 ГБ (LibreOffice до 1,1 ГБ на шаблоне ЛЦТ плюс python-pptx), API 512 МБ, Valkey 256 МБ с `maxmemory 128mb noeviction` (очередь не должна тихо терять задания), Caddy 192 МБ, интерфейс 64 МБ. Сумма пределов больше 3,9 ГБ сервера сознательно: пределы — потолок, а удержание в реальной памяти обеспечивают слоты рендера (`PD_RENDER_SLOTS=2`, на этом сервере третий слот не выделять). Логи — json-file с ротацией 20 МБ × 5; у воркеров healthcheck по регистрации в Valkey; `stop_grace_period` 60 с, чтобы задача дошла до границы этапа. Число реплик и слоты — один рычаг в `.env` сервера, приложение получает те же значения через `PD_QUEUE__GENERATION_WORKERS` и `PD_RENDER__SLOTS`.

## 2026-09-16. Caddy без HTTP/3

В Caddy включены только h1 и h2, UDP 443 наружу не публикуется. Причина измерена на проверке этапа 3: в Firefox запросы шли по HTTP/3 и дважды зависли на 9,6 с при свободном сервере (в трассе Playwright всё время в `wait`, на API запросы пришли через 9 с новыми upstream-соединениями Caddy) — стойло QUIC по UDP за VPN разработчика. Для сервиса с загрузками и опросом состояния h2 достаточно, а один транспорт предсказуемее. Тайм-ауты входа согласованы с API: заголовки 30 с, тело 10 мин (загрузка до 100 МБ на медленном канале), ответ upstream 10 мин (заголовки ответа приходят после приёма всего тела).

## 2026-09-16. Выпуски с тегами, миграция до запуска и откат одной командой

Образы получают тег `<commit>[-dirty]-<время>`; `deploy.sh` на сервере сначала выполняет `maintenance migrate` новым образом (перед изменением схемы — полная резервная копия), затем `up -d`, затем ждёт `status: ok` в `/api/health`, а не просто HTTP 200. Выпуск записывается в `deploys.log` вместе с предыдущим тегом и версиями схемы, копия репозитория выпуска сохраняется в `releases/<тег>`; хранятся три последних выпуска с образами. `--rollback` возвращает предыдущий выпуск: образы, compose-файлы из `releases/`, при изменённой схеме — базу из копии перед миграцией (`--only-db`, загрузки и артефакты остаются, текущая база откладывается). Миграции SQLite остаются прямыми (forward-only); откат схемы — восстановление копии, что честно теряет строки, появившиеся после миграции, и поэтому документирован как шаг с ценой. Принудительный `docker build --pull` убран: базовые образы закреплены точными тегами, а проверка метаданных упирается в лимит анонимных запросов Docker Hub (429 на сервере).

## 2026-09-16. Резервная копия одним tar и логический дамп Valkey

Копия — один tar без сжатия: `meta.json`, снимок SQLite через backup API (живая база в WAL одним файлом не копируется), логический дамп Valkey (DUMP/RESTORE с TTL, без регистраций воркеров и служебных отметок), загрузки и артефакты без временных каталогов. Логический дамп выбран вместо копирования тома Valkey: он идёт по сети из контейнера API, не требует доступа к тому и не зависит от политики AOF/RDB; очередь — транзитное состояние, источник истины о заданиях — SQLite, а задания, выполнявшиеся в момент копии, после восстановления помечает сверка. Согласованность обеспечивается порядком (база → очередь → файлы) и свойствами хранилища: файлы неизменяемы и адресуются по sha256, ревизии публикуются атомарно. Восстановление проверяет копию на staging-каталогах (ссылки файлов, манифесты, sha256 артефактов) и откладывает текущие данные в `.previous-<время>`, а не удаляет. Материалы организаторов в копию не входят: они не данные пользователей и восстанавливаются копированием с машины разработчика.

## 2026-09-16. Сборка мусора с отметками и грацией

Сироты (задания и пакеты удалённых проектов с артефактами, файлы без ссылок, каталоги без строк в базе) не удаляются при первой встрече: сборка мусора ставит отметку в таблице `gc_marks` (миграция 2) и удаляет объект, когда отметка старше срока из `retention` в `config/app.yaml`. Отсчёт от момента обнаружения, а не от времени файла: так грация одинаково защищает промежуточные состояния (файл сохранён, но ещё не привязан; задание создано, а проект ещё не обновлён) и не зависит от возраста данных. Шаблоны — библиотека сервиса: они не сироты, пока есть их строка, и живут вместе с байтами и заданиями анализа; убирает шаблон только явный `DELETE /api/templates/{id}` (строка и миниатюры сразу, задание анализа и байты — сборка мусора по сроку). Задача ставится API в очередь `analysis` раз в `gc_interval_s` через ключ Valkey (SET NX), выполняется воркером анализа, каждое удаление пишется в его лог, сводка — в `runs/gc/last.json` и `/api/health`. `DELETE /api/projects` по-прежнему не удаляет артефакты немедленно: это делает сборка мусора по сроку.

## 2026-09-16. Имя воркера без PID, ранний обработчик SIGTERM, срок регистрации 90 секунд

На проверке перезапусков этапа 3 воркер после аварийного падения уходил в цикл перезапусков до семи минут: имя строилось из PID (в контейнере всегда 1), а RQ отказывается стартовать при живом ключе прежнего процесса до истечения его TTL. Теперь суффикс имени случайный, при старте воркер снимает регистрации прежних процессов своего контейнера (в контейнере один воркер, поэтому любая другая запись с тем же hostname — след упавшего), а срок регистрации в Valkey равен `queue.heartbeat_ttl_s` (90 с) вместо 420 с RQ, чтобы после пересоздания контейнеров `/api/health` недолго считал старые записи живыми. Отметка проверки рендерера получила срок жизни неделя. Второе: процесс воркера — PID 1 контейнера, а ядро не применяет к PID 1 действие по умолчанию, поэтому до установки обработчиков RQ (в `work()`) SIGTERM игнорировался и `docker stop` во время старта ждал всю грацию (60 с); на время старта поставлен свой обработчик с немедленным выходом.

## 2026-09-16. Адаптер моделей без instructor: проверка ответа и повтор с подсказкой свои

Рассмотрен instructor (FRAMEWORKS §5). ## 2026-09-16. Лимитер Valkey переподключается к текущему циклу событий

На сервере анализ ЛЦТ оставлял в Valkey четыре неосвобождённые аренды, и следующий анализ ждал квоту до истечения TTL. Причина: клиент `redis.asyncio` создавался один раз и был привязан к первому циклу событий, а синхронные вызывающие (воркер RQ, CLI) запускают `asyncio.run` несколько раз за процесс — во втором цикле освобождение аренды падало после того, как аренда уже была взята. Теперь `ValkeyLimiter` перед каждой операцией сверяет цикл и пересоздаёт клиент (регрессионный тест `test_valkey_limiter_survives_multiple_event_loops`); аренды по-прежнему истекают по TTL как последняя защита. Локальные прогоны ошибку не показали: без Valkey работает лимитер процесса.

## 2026-09-16. Импорт содержания: парсеры по формату в общую модель блоков, кэш разбора по файлу

Каждый формат разбирает свой модуль (`parsing/content/parsers`) в одну модель блоков с местом в источнике, таблицы и изображения — отдельно; сквозные идентификаторы пакета назначает сборка в порядке файлов. Скилл `variant_planner` 0.2.0 (промпт `plan.slides` 0.2.0, рассуждение выключено, бюджет `time_budget_s` 100 с на вариант при `stage_plan_s` 120) получает не профиль шаблона, а пакет тезисов общего StoryPlan (до `plan.packet_theses` = 5, разделы не рвутся), факты со значениями только для справки, наборы данных, изображения, короткий список композиций с ёмкостью в символах (`matching.py`: по подаче тезиса, вместимости, уверенности анализа и предпочтениям варианта; таблица только при слоте таблицы, диаграмма — при слоте диаграммы или картинке диаграммы в образце роли `chart`) и правила оси плотности. Модель возвращает короткую схему (тезисы слайда, композиция из списка, заголовок, пункты, факты, набор данных, изображение); слоты, подстановку фактов, измерение и покрытие собирает код. Пакеты одного варианта идут параллельно под общим deadline (`asyncio.gather` в одном `asyncio.run`, одновременность ограничивает лимитер), три варианта — на трёх воркерах; общее содержание не переписывается трижды: тезисы, факты и данные общие, вариант меняет группировку, композиции, объём формулировок и визуализацию. Титульный, разделители, содержание и финальный слайд подбираются по ролям кодом; призыв к действию идёт заголовком финального слайда только если помещается по измерению, иначе получает отдельный слайд. Без настроенного провайдера слой падает `plan_llm_not_configured`; детерминированный черновик (`drafts_without_model`) доступен только CLI `--no-model` и тестам на реальных профилях и помечается в плане.

## 2026-09-16. Лестница ёмкости по измерению, а не по символам; переполнение записывается, а не теряется

Ёмкость слотов из профиля (символы) — ориентир для модели; решение принимает измерение текста после подстановки фактов по файлам шрифтов рендерера (`capacity.py`: перенос по словам через FreeType, высота строки из метрик файла, интервалы и поля образца, запас 0,92). Лестница при переполнении: более вместительная композиция среди кандидатов при исходных кеглях → кегль из шкалы шаблона не ниже `plan.min_font_ratio` = 0,75 исходного и порогов по роли (`min_body_pt` 12, `min_title_pt` 20) → сокращение без потери обязательного (пункты и предложения без ссылок на факты, части заголовка после двоеточия или запятой) → разделение слайда в пределах диапазона. Повтор модели ограничен одним запросом на пакет с измеренными переполнениями (новый запрос — новый ключ кэша, поэтому воспроизводим в replay); дальше переполнение остаётся в плане структурированно (`fit.action = overflow`, предупреждение `capacity_overflow`) и уходит в аудит — и при диапазоне, и при точном числе слайдов (до 18.09 при точном числе план не выдавался с ошибкой `plan_capacity`; в шаблоне со строчными слотами на 52–112 символов это оставляло пользователя без единого варианта, а исправить одну строку из чата проще, чем потерять колоду). Подписи-наполнители (сообщение, пояснение) в необязательных слотах при переполнении убираются, а не режутся. Крошечные обязательные слоты (единицы измерения, номера шагов, до 12 символов) сохраняют текст образца и не предлагаются модели. Большие наборы данных планировщик делит между слайдами (`table.row_offset`, только подробный вариант и в пределах диапазона), иначе усекает с предупреждением `table_truncated`; композер страниц не добавляет. Диапазон числа слайдов по умолчанию (`limits.slide_count_default`, когда ни запрос, ни бриф его не задают) — ориентир, а не требование: если содержания не хватает на нижнюю границу (один xlsx даёт пять тезисов), план выдаётся короче с предупреждением `slide_count_relaxed` и фактическим диапазоном в `slide_count`; явно заданный диапазон или точное число при нехватке содержания дают ошибку `plan_slide_count`.

## 2026-09-16. Кэш готовых планов в каталоге, различимость вариантов — предупреждение, а не переименование

Готовый SlidePlan кэшируется в `data/plan-cache` (`PlanCache` на том же `FileCache`, что и ответы модели) по ключу из `content_hash` StoryPlan и дайджеста его тезисов, структуры и ёмкости паттернов профиля (без превью и путей), манифеста шрифтов рендерера, варианта, требования к числу слайдов, языка и seed, настроек `plan.*`, версий скилла, промпта и схемы, модели; при попадании подставляются идентификаторы задания (`plan_id`, `template_id`, `package_id`, `story_id`) и отмечается `generation_meta.cache_hit`, стадия `plan` варианта несёт `cache_hit`. Каталог — производное состояние: в резервную копию и сборку мусора не входит, как `llm-cache`. Различимость трёх планов проверяется по последовательности композиций и способам визуализации (`compare_plans`): одинаковая последовательность паттернов сама по себе допустима, если визуализация различается; пара без различий записывается предупреждением `variants_indistinct` в планы (CLI) и в задание (`task_finalize`), а не маскируется переименованием — на шаблоне из четырёх паттернов (`tests/fixtures/pptx/mini_template.pptx`) balanced и detailed совпадают, и это видно в результате. Контракт `slide_plan` 1.2 (набор 1.4): `fit` у блоков, `row_offset` у таблиц, `target` у числа слайдов, блок chart в слоте image паттерна роли chart (картинка диаграммы образца заменяется нативной диаграммой на этапе 8); валидатор `check_slide_plan` допускает только это исключение.

## 2026-09-16. Вёрстка: исходный пакет как основа, клон образца на слайд, заполнение по element_ref

Слой `layout` (этап 8) не строит презентацию с нуля: исходный PPTX открывается python-pptx как рабочая основа, для каждого слайда плана клонируется образец паттерна (`ooxml.clone_slide`: макет и картинки общие, диаграммы с книгами данных копируются), слоты заполняются по `element_ref` профиля, поэтому профиль сверяется с файлом по `template_hash` — на другом файле ссылки недействительны (`compose_template_mismatch`). Текст заменяется с сохранением `a:pPr` и оформления первого фрагмента, кегль из `fit.size_pt` плана ставится явно на каждом фрагменте, масштаб `normAutofit` образца снимается: результат не зависит от автоподбора PowerPoint. Многострочный текст ложится на абзацы образца, если их несколько (заголовок карточки крупнее описания), списки — на маркированный абзац образца. Незаполненные текстовые слоты удаляются (заглушки образца в результат не попадают), крошечные слоты (номера шагов, единицы) заполненных карточек сохраняют текст образца и помечаются в ComposedDeck `content_source: sample` — аудит `integrity.placeholder_text` не считает их заглушками; карточки без содержимого удаляются целиком по `removable_object_ids` (группы с равным числом карточек считаются одной карточкой по индексу), пустые рамки карточек — по геометрии, статика и логотипы остаются. Образцы удаляются в конце; python-pptx пишет только части, достижимые от корня, поэтому недостижимых частей в результате нет (проверяется `layout/integrity.py`). Числа в крошечных слотах получают `wrap="none"`: LibreOffice считает текстовую область эллипса уже прямоугольника и рвал «27» на две строки. Новые объекты (диаграммы, таблицы, схемы) получают свежие id, а не заполняют пропуски удалённых, чтобы `removed_object_ids` и новые объекты не путались. Заметки образца не клонируются (0A), заметки создаются из плана.

## 2026-09-16. Нативные таблицы и диаграммы по образцу, диаграмма на месте картинки

Таблица образца перестраивается под набор данных: первая строка — шаблон заголовка, остальные — шаблоны строк по кругу (полосы образца сохраняются, последняя строка образца при трёх и более не попадает в цикл как вероятный итог), ячейки копируются с `a:tcPr` (границы, заливка, отступы) и оформлением фрагментов, сетка колонок берёт пропорции образца с минимальной шириной колонки 1,6 млн EMU (PowerPoint рисует таблицу по сумме `gridCol`, а не по `ext` кадра — у VK Education кадр 3 млн EMU при сетке 10,9 млн). Без таблицы в образце — `add_table()` со стилем темы. Диаграмма образца того же семейства (категорийная, круговая, точечная) получает `replace_data()` и сохраняет оформление; иначе или на месте картинки диаграммы (паттерн роли chart, слот image) строится новая `add_chart()` с акцентами темы (слишком светлые акценты отбрасываются), шрифтом и кеглем профиля, легендой и подписями по плану; для картинки диаграммы из нескольких изображений (VK Tech: столбики — отдельные картинки) область — объединение всех слотов image паттерна, лишние картинки удаляются. Формат чисел — по ряду (дробные с одним знаком), ось — `General`. Схемы (process, cycle, pyramid, hierarchy, matrix, funnel, timeline, venn) собираются из фигур и соединителей в группе — это редактируемые фигуры, не SmartArt (FRAMEWORKS.md §7; SmartArt образца удаляется вместе с частями); шевроны для процесса не используются — LibreOffice выводит в них текст по букве в строку.

## 2026-09-17. Планировщик 0.3.0: композиция по объёму содержания, добор без слайдов из одного пункта

Первая настоящая колода на VK Education (бриф без материалов, диапазон 15–18) показала, что вёрстка в стиле шаблона, а слайды пустые: модель клала один-два пункта на композиции из 4–7 карточек, компактный вариант убирал необязательные тезисы и возвращал их кодом слайдами из одного пункта, недобор до нижней границы добирался делением списков на «(продолжение)», подпись карточки склеивалась с текстом через тире, а две колонки списков получали по одному пункту (остальные терялись). Решения: промпт `plan.slides` 0.3.0 требует композицию по объёму (не меньше N−1 пунктов на N карточек), не оставляет слайд из заголовка и одного пункта, раскрывает тезис по сторонам вместо деления списка, `sub` — только при слоте подписи; код проверяет то же и без модели: `thin_ratio`/`right_size_pattern` меняют композицию на ближайшую по объёму, `density_hint` и `count_hint` дают модели один повтор пакета, необязательные тезисы компактного варианта убираются только при избытке содержания, нижняя граница пакета — 0,7 цели для всех вариантов, добор идёт слайдами в стиле шаблона (итог — композицией цитаты, разделители, оглавление, раскрытие из пояснения) раньше деления, слайд из одного пункта — только ради точного числа. Явный диапазон при нехватке содержания даёт короткую колоду с `slide_count_short`, а не ошибку: интерфейс всегда шлёт диапазон, и отказ был бы отказом всему проекту. Колонки списков делят пункты между собой (`item_capacity` = колонки × пунктов). ## 2026-09-17. Шрифты Microsoft в образе воркера, метрические клоны — не подмена

## 2026-09-19. Медиа ревизии и ресурсы шаблона по HTTP, превью макетов для холста

Холст редактора рисует слайд из объектов ComposedDeck в браузере, а картинки лежат внутри PPTX. Композер выкладывает использованные ресурсы колоды в `media/` каталога ревизии (`layout/media.py`), имя артефакта пишется в `assets[].artifact`, файлы попадают в манифест ревизии и отдаются обычным `GET …/artifacts/{name}`; медиа дублируется в каждой ревизии (единицы МБ, только использованные ресурсы) ради простоты манифеста и отката. Объекты макета и мастера (фон, декор, логотипы) в ComposedDeck не входят, поэтому анализатор при рендере дополнительно собирает временный PPTX из пустых слайдов макетов, на которые ссылаются паттерны, и кладёт `previews/layout-<layout_id>.png` (`ANALYZER_VERSION` 0.2.3; шаблоны библиотеки переанализируются `reanalyze-templates`); холст кладёт такую картинку нижним слоем, а таблицы, диаграммы и прочие объекты, которых не умеет рисовать, показывает вырезкой из миниатюры ревизии.

## 2026-09-21. «Готово» и «Редактировать» сверяются снимками: заливка темы, произвольные фигуры, межстрочный

Холст редактора рисует объекты ComposedDeck, а «Готово» показывает PNG, отрендеренный
LibreOffice из того же PPTX. Совпадение этих двух картинок теперь измеряется, а не оценивается
на глаз: снимок одной и той же рамки в обоих режимах, доля точек с разницей больше 40 из 255.
На колоде ЛЦТ-2026 (25 слайдов) расхождение упало с 22,4 % до 0,9 % на худшем слайде.

Что было починено по одному:

- **Заливка и контур из стиля темы.** У фигуры, нарисованной в PowerPoint инструментом,
  `p:spPr` пуст, а цвет живёт в `p:style/a:fillRef` (номер заливки темы + цвет ссылки). Белая
  плашка на полслайда в ComposedDeck не попадала вовсе. Тема запоминает виды заливок
  (`a:fmtScheme/a:fillStyleLst`), заливка резолвится как контур по `a:lnRef`; градиент темы
  рисуется основным цветом — приближение, но вид записан честно.
- **Фигуры произвольной формы** (`a:custGeom`) помечаются `geometry: "custom"`: прямоугольником
  их рисовать нельзя — вместо тонкого контура мокапа телефона получался чёрный блок. Холст
  показывает такую фигуру вырезкой из миниатюры, HTML-экспорт не рисует ей ни заливки, ни
  контура. Группа таких фигур (иконка, схема) показывается одной вырезкой на группу: 670
  отдельных вырезок браузер не тянет, а по одной фигуре картинка всё равно не собирается.
  Группы с текстом остаются живыми — текст правится и не дублируется вырезкой.
- **Разделители нулевой высоты**: `box-shadow: inset` на фигуре высотой 0 не виден, и линии
  между блоками пропадали и на холсте, и в HTML. Теперь такая фигура рисуется заливкой нужной
  толщины.
- **Межстрочный интервал**: `a:lnSpc/a:spcPct` 100 % — это одинарный интервал шрифта
  (ascent + descent + gap), а не `line-height: 1`. Строки на холсте стояли на четверть теснее.
  При 100 % межстрочный не задаётся вовсе (браузерный `normal` совпадает с рендерером), для
  других процентов считается от одинарного: на сервере — тем же `text_metrics`, что мерит
  ёмкость слотов, на холсте — измерением гарнитуры скрытым образцом.
- **Отступ перед первым абзацем** рамки не ставится: рендерер его не добавляет, и весь текст
  на холсте стоял на строку ниже, чем на слайде.

Осталось приближением и записано как долг: у объекта в ComposedDeck один стиль на абзац, а не
на фрагмент, поэтому «**Капитан:** ФИО» на холсте целиком жирный; маркеры списков из мастера
не наследуются; пустые плейсхолдеры рендерер показывает подсказкой («Фото команды»), а холст
их не рисует; заливка и контур плейсхолдера не наследуются от макета.

## 2026-09-23. Диаграммы-картинки шаблона и готовой презентации: модель читает устройство, значения меряет код

В загруженных PPTX диаграммы часто лежат картинками (в шаблоне VK Education на слайдах 45–50 — двенадцать PNG по 600 px, частей `ppt/charts/` нет), и в редакторе их не поправить. Решение Александра: такие картинки заменяются нативными диаграммами сразу при загрузке, значения без подписей **меряются по пикселям и помечаются** «восстановлено по картинке». Модель (скилл `chart_reader`, роль vlm) только описывает устройство: вид, ряды и их примерные цвета, категории, подписи делений и напечатанные значения. Числа и точные цвета — код (`parsing/raster_charts/`): палитра картинки, калибровка шкалы по равномерной последовательности строк подписей, развёртка кольца по углу, края столбцов, точки линий в центрах категорий, верхнее ребро областей. У каждой точки есть происхождение: `label` (подпись, точно), `measured`, `inferred` (закрыта другими рядами — продолжение видимого ребра или не выше закрывающего ряда), `model` (оценка модели, последний резерв). Мера, расходящаяся с подписью больше допуска, отклоняет чтение, и картинка остаётся картинкой. Это отдельный путь от `chart_extractor` Василисы: там извлечённые данные становятся фактами для новых слайдов, и правило «только подписанные значения» не меняется. Здесь восстанавливается то, что уже нарисовано на месте картинки. Серия этапов 26–29; этап 26 — чтение (CLI `read-charts`), запись нативной диаграммы и замена при загрузке — этапы 27–28.

## 2026-09-24. Сборка стартует сама, первый вариант — один, число слайдов по умолчанию не просьба

Замечания Александра по живому серверу. Шаблон и текст задачи есть — сборка стартует сразу: вопроса о режиме оформления нет (по умолчанию смешанный, сменить можно фразой «строго по шаблону»), назначение не обязательно (смысловой план берёт `other`), карточки задачи с кнопкой «Сгенерировать» нет — в ленте одна фраза «Понял задачу: … Собираю презентацию…» и ход задания. Шаблона нет — чат просит выбрать его, и выбор запускает сборку; выбор уже разобранного шаблона пишет «Выбрал шаблон «X»», а отчёт «Разобрал шаблон… за N с» остаётся только загрузке PPTX шаблоном. Карточка задачи с «Сгенерировать заново» появляется, только когда презентация уже есть и сменился шаблон или содержание.

Варианты больше не стартуют одновременно: планы упираются в модель, и три плана делили её между собой — первый готовый появлялся через 1,5–3 минуты (серверные задания 23.09: план 50–166 с на вариант, сборка и экспорт 10–20 с, аудит ~30 с). Теперь первым собирается `balanced` (`jobs.PRIMARY_VARIANT`), остальные ставятся в очередь за ним (зависимость RQ с `allow_failure`, при его ошибке тоже идут) и доделываются, пока человек смотрит первый. В шапке переключатель всех вариантов: неготовые — с загрузкой и без нажатия, выбор открывает PPTX варианта; первый готовый закрепляется выбором, доделанный следом вариант открытую презентацию не подменяет.

Число слайдов: диапазон 10–15 по умолчанию в запрос не уходит (`slideCountAsked`), в ленте не называется, нехватка содержания на него молчит (`slide_count_relaxed` только в плане). Просьба пользователя — точное число или диапазон — при нехватке содержания даёт короткую колоду, а не отказ всех вариантов, и фразу задания «Просили N слайдов — содержания хватило на M…» (`slide_count_short`). Переполнение точного числа по-прежнему ошибка плана (решение от 19.09 про переполнение касается вёрстки, не плана).

## 2026-09-24. «Открыть как презентацию»: копия синхронно в API, диаграммы отдельной ревизией, контекстный аудит выключен

Замеры 23–24.09 на izbox.ru: колода VK Education (55 слайдов) открывалась за 30 с при свободной очереди и до 4 минут при занятой, хотя редактору нужны только байты PPTX. В пути до показа стояли ожидание воркера `generation` (там же импорт содержания и чужие сборки), чтение диаграмм-картинок моделью (около 40 с при холодном кэше) и контекстный аудит, который держал задание и воркер две минуты.

Решение. Копия файла публикуется ревизией r1 прямо в `submit_generation` — без очереди, модели и разбора пакета (число слайдов — по списку в `presentation.xml`); ошибка копии запрос не роняет, копию тогда делает фоновая задача. Подписи пустых плейсхолдеров в синхронный путь не вошли: сохранение пакета python-pptx на 55 слайдах на сервере — 0,73 с, всё вместе 0,92–1,03 с, больше секунды из плана; они идут в фон вместе с диаграммами. Фон открытой презентации (подписи, диаграммы, рендер PDF и миниатюр) — очередь `interactive`, которую воркеры генерации берут раньше `generation`. Если в копии что-то изменилось, результат — ревизия r2 с `charts.json`, r1 не переписывается: офисная копия r1 создаётся один раз по своему `source`. Полная сборка пишет в последнюю ревизию и повторяет её замены; `ready_at` ставится первой публикацией и больше не переписывается (раньше сборка затирала его своим временем, и `first_file_ready_ms` врал). Редактор сам переключается на новую ревизию, если документ не правили; признак правки — сохранённые версии и сигнал ONLYOFFICE `onDocumentStateChange`, а не `active_key`, который ставится при любом открытии. Правка слайда из чата до готовности плана принимается и ждёт разбора (`depends_on` на задачи генерации, база переносится на последнюю ревизию), чат говорит срок. Контекстный аудит для `original` по умолчанию выключен (`run_contextual_audit: false` в `openAsDeck`), детерминированные проверки остаются; проверить слайды моделью можно из подробностей задания — это то же задание с включённым аудитом.

Сверх плана этапа: смысловой план по профилю, сборка варианта `original` и итог задания без контекстного аудита тоже идут в `interactive`. Замер на сервере с двумя чужими сборками трёх вариантов показал, что в очереди `generation` эти восемь секунд работы без модели ждали чужих вариантов больше десяти минут, а вместе с ними — правка из чата. Правка ждёт только сборку варианта, а не итог задания. Если задачи разбора всё же стоят в очереди (оба воркера заняты долгими задачами), фраза в чате говорит об очереди, а не обещает срок.

## 2026-09-24. Голосовой ввод: GigaAM-v3 e2e в ONNX int8, свои признаки, фразы режет браузер

Кнопка микрофона в чате по просьбе Александра. Модель — GigaAM (Сбер, MIT, 220 млн параметров, укладывается в допуск ТЗ): линия `v3_e2e_ctc`, единственная со знаками препинания и нормализацией текста — для реплик в чат это важнее последних долей WER. Сервер izbox.ru — 2 vCPU и 3,9 ГБ, из них около гигабайта у ONLYOFFICE, поэтому граф экспортируется в ONNX и квантуется динамически в int8 (320 МБ против 886 МБ fp32); контрольные фразы int8 и fp32 совпадают слово в слово, кроме одной буквы в одном слове из 150 (WER 0,7 %), — рабочим оставлен int8. Модель живёт в отдельном сервисе `asr` с пределом памяти 768 МБ, грузится по первой фразе и выгружается после 10 минут простоя: диктуют редко, держать полгигабайта постоянно незачем.

torch в образах стека не ставится: признаки считает свой код на numpy, а torch нужен только скрипту экспорта на машине разработчика. Окно и мел-фильтры берутся из весов, а не вычисляются: в чекпойнте они округлены, и с точными буферами признаки в тихих полосах расходились с обучением на единицы в лог-шкале.

Модель офлайновая и принимает записи до 25 с, а длинные записи библиотека режет pyannote с токеном Hugging Face. Вместо этого фразы режет браузер — детектор по энергии, 700 мс тишины — и шлёт по одной: текст появляется фраза за фразой, pyannote и токен не нужны. Аудио не хранится ни в API, ни в сервисе, в журнал идут только длительности. Роль `asr` записана в `config/models.yaml` и MODELS.md, но в `versions.models` результата генерации не попадает: перечисление ролей там — часть контракта, а распознавание речи в генерации не участвует.

## 2026-09-24. Выбор слайда и объекта в живом редакторе — через внутренний API ONLYOFFICE, пересобранный слайд переносится в копию

Александр хочет выбирать слайд или объект прямо в редакторе и говорить чату, что изменить.
Публичного способа узнать выбор нет: коннектор (Automation API) — платная редакция, плагины
выключены. Используем внутренний API редактора в том же окне, что и сохранение (уже зависим от
него, версия закреплена образом 9.3.1): события строки состояния и панели свойств
(`asc_onCurrentPage`, `asc_onFocusObject`) и публичные геттеры свойств фигуры. Проверка наличия
методов при каждом открытии; нет их — моста нет, прежнее поведение. Альтернатива — системный
плагин, который шлёт выбор родителю, — отвергнута: включение плагинов меняет конфигурацию
редактора и безопасность, а данных дало бы не больше.

Правка слайда моделью строит слайд по плану варианта, поэтому ручные правки открытой копии в неё
не попадают. Вместо баннера «Доступна другая версия» (при открытом редакторе недоступного)
пересобранный слайд переносится в копию: один слайд из новой ревизии встаёт на место старого,
остальные слайды копии не трогаются. Объект правится в самой копии, как `/edit` с адресом; сервер
находит фигуру по имени и рамке, потому что номер фигуры редактор наружу не отдаёт.

место одну нативную диаграмму, у которой числа — её данные. Модель не зовётся: форма и цвет
читаются по пикселям и рамкам фигур, числа — из надписей, поэтому поиск быстрый (1–2 с на
шаблон), детерминированный, и полная сборка повторяет его сама, без записанных чтений.

Правило значений (решение принято в сессии и сообщено Александру): если числа сходятся с рисунком —
берутся числа; если нет — значения снимаются по рисунку (у кольца доля окружности, у столбцов
пропорционально длине, самый длинный равен самому большому числу) с пометкой «проверьте». Иначе
«10» на всех столбцах разной высоты сделали бы их одинаковыми, а «10%» в каждом кольце — одной
дугой. Для материалов-фактов правило `chart_extractor` «без выдумывания» не меняется.

Остаток кольца во встроенной книге — формула `=100-B2`: книгу пишет xlsxwriter, который уже стоит
как обязательная зависимость python-pptx (openpyxl не пишет кэш значения формулы). Под ONLYOFFICE
подобраны три приёма, проверенные рендером сервера: размер подписи в центре кольца (иначе число
ломается по знакам), запас рамки (иначе подпись прижимается к краю) и подписи по центру полос при
развёрнутой оси (ONLYOFFICE зеркалит сдвиг «внутри у конца»).

## 2026-09-24. Контракт операций чата и снимок колоды: одна форма из обоих миров, связь по именам фигур

Этап 36 серии «чат как редактор». Появились две
схемы.

`chat_ops` 1.0 — операции таблицы 4.2, 95 штук в 11 семействах. У каждой операции:
- адрес в снимке ревизии `base` — слайд, объект с путём групп, абзац, фрагмент, ячейка, список

Адрес объекта принимает и придуманный идентификатор своей надписи: иначе `add_text` и

`deck_snapshot` 1.0 строится по байтам PPTX тем же обходом и разрешением стилей, что
ComposedDeck. Две отдельные реализации (из ComposedDeck и из XML копии) расходились бы в
группах, наследуемых рамках и стилях. Поэтому источник у снимка один — файл, а ComposedDeck и
план лишь добавляют слайд плана, слот и роль. Карта объектов копии для выделения и правки на

## 2026-09-26. Диаграммы в копии — через python-pptx, числа только из просьбы (этап 40)

Правки на месте (этап 38) меняют только XML слайда, а у диаграммы данные лежат в части
`chart*.xml` и во встроенной книге. Поэтому операции `chart.*` и смена подачи

прислать сами числа. Новая таблица или диаграмма не встаёт в место меньше четверти ширины и
трети высоты слайда и не закрывает текст: тогда берётся самый большой свободный прямоугольник,
а если его нет — отказ с подсказкой. В план варианта правки на месте по-прежнему не пишутся.

## 2026-09-28. Подписи фактов по-русски, таблица закрывает факт из текста, пояснения без «(продолжение)»

По итогам прогонов Luna (`docs/luna-presentation-quality.md`). Подписи вида «Среднем: 27» и
«Затратах на пилот: 2,4 млн ₽» шли из извлечения: «в среднем» перед числом принималось за

наречие меры отбрасывается (показатель — слово после числа: «27 уведомлений в день»), первое
слово показателя приводится к именительному по окончанию «-ах/-ях» (`facts._nominative_plural`),
а пункт для числа, считающего слово после себя, берётся отрезком исходной фразы
(«В среднем 27 уведомлений в день на человека»). Ячейку таблицы называет строка («Затраты на
пилот: 2,4 млн ₽»), а не колонка «Сумма»; строка-период уточняет колонку («Открываемость, май»).

Итоговый слайд detailed переполнялся: под таблицей экономики дописывались те же суммы строками
списка, потому что факт из текста документа (`12,5 млн ₽`, источник docx) и ячейка таблицы
(`12,5` в колонке «Сумма, млн ₽», источник xlsx) считались разными. `variants._labelled_table_facts`
признаёт факт показанным, если ровно одна видимая ячейка совпадает по значению с учётом
множителя колонки, единице и словам показателя в подписи строки, а цифры периода видны.
Если пояснение к таблице всё равно не помещается при потолке числа слайдов, страницу под него
отдаёт разделитель раздела (потом оглавление): слайд с одним названием раздела стоит меньше,
чем текст, ушедший бы в заметки. Страница пояснений называется главной мыслью слайда, а не
«… — пояснения»; вторая страница пояснений повторяет заголовок, и `_distinct_titles` даёт ей
формулировку тезиса вместо «(продолжение)».

Записи ответов модели для тестов перезаписаны через мост к Claude Sonnet (подписи фактов входят
в текст запроса, старые записи перестали подходить); правило про это — в CLAUDE.md.

## 2026-09-29. Оформление собственных композиций по правилам «заполняй страницу»

Просмотр четырёх колод организаторов на текущем коде показал, что слайды выглядят пустыми
не из-за нехватки картинок, а из-за композиций: карточки занимали верхнюю треть над пустым
полем, «крупное число» жило в левой половине при пустой правой, обложка на своей композиции
была плоским заголовком. За ориентир взят гайд по дизайну колод GenOffice (Apache-2.0): 
заполнять страницу, крупный текст, одна акцентная система, без полосок-украшений, у
обложки визуальный якорь. Сделано в `library/dress.py` и `library/geometry.py`, без модели,
проверено перерисовкой (`scripts/rerender.py`) и обоими наборами тестов:
- карточки: кегль растёт до 1,6 (было 1,4), пока группа занимает меньше 80 % области;
  плашки занимают не меньше 72 % рабочей области (`CARD_FILL`), лишняя высота делится
  между рядами; карточка с одним заголовком центрирует значок и заголовок по высоте;
- полоса-украшение по верху плашки убрана: иерархию держат заливка, кегль и вес;
- «крупное число»: число с подписью столбиком по центру левой половины (кегль от
  4 × заголовка, подпись кеглем подзаголовка), пояснение списком в правой половине по центру
  той же высоты (`_hero_layout`, слоты в `build_hero_number`);
- обложка и финал на своей композиции: цветной блок акцентом в правых 37 % слайда
  (`_dress_cover`), текст в левых 60 %, заголовку треть высоты под кегль 1,4 × заголовка;
  рамки при этом не двигаются — их место задано композицией, инвариант тестов
  `test_typography` сохранён;
- заголовок обложки без приписки «Концепция:»; пунктов «Содержания» не больше, чем мест
  в композиции (седьмой раздел вставал в заголовочную строку образца ЛЦТ).
Что осталось видимого: нерелевантные фото из Openverse (рамка, вывеска Texaco), образец
VK Tech с макетом-иллюстрацией без содержания, узкие рамки образцов с мелким текстом.

## 2026-09-29. Фоновый декор шаблона на пустотах слайдов

Содержательные слайды на светлых макетах (VK Education, VK Tech) выходили белым листом, хотя у
шаблона есть узнаваемая графика обложки: буквенный узор, стеклянный куб. Декор не задаётся
руками ни для одного шаблона:
- **Кандидаты — по устройству файла** (`assets.decor_candidates`): картинка позади текста (в
  макете, мастере или ниже всех текстовых объектов слайда), с прозрачным фоном (15–97 %
  прозрачных пикселей), крупнее значка, не логотип и не QR.
- **Декор среди кандидатов выбирает VLM** (`template_analyzer` 0.3.0, промпт
  `analyze.pick_decor`): один лист с номерами и подписью, где каждый стоит. Модель отвечает,
  фирменный ли это декор (фото, скриншоты, мокапы, схемы, логотипы — нет), можно ли резать его
  краем слайда (узор, свечение — да; цельная фигура вроде куба — нет) и оценивает мотив
  (0–10). Цвет и яркость модель не судит: бледность делает код, иначе она отбрасывала цветные
  версии узора. Без модели декора нет — по файлу узор от иллюстрации не отличить. Выбранное —
  теги `decor`, `decor:<оценка>`, `decor-crop` у ресурса профиля (анализатор 0.4.7).
- **Расстановка — `library/motif.py`**, на содержательных слайдах своих композиций и образцов
  (не обложка, раздел, финал): свободное место считается по тексту, а не по рамкам; мотив
  встаёт у края, к которому прижат в шаблоне (занят — у другого), и выдвигается из-за края
  ровно до содержания; узор может уйти за край больше чем наполовину, цельная фигура — только
  у бокового края, не меньше 10 % слайда и почти целиком (по плотной части, без свечения).
- **Заметность, а не прозрачность**: для слайда берётся лучший по оценке мотив, а при равной —
  самая контрастная к фону расцветка (белый узор на белом не ставится); непрозрачность — по
  разнице светлоты с фоном (8–25 %). Обрезка и прозрачность запекаются в PNG: одинаково в
  ONLYOFFICE, PowerPoint, PDF и HTML.
- **Где не ставится**: макет несёт свой декор (полосы WorkSpace); на слайде фото; место, где у
  картинки-фона макета есть границы — панели, нарисованные прямо в фоне (VK Tech «Содержание»,
  «Контент»), структура файла не видит, их видно только по карте границ картинки.
- Служебные линии макета целиком за краем слайда (Education) края не запирают.
- В разборе слайда для чата картинка «Декор шаблона» — оформление, а не картинка содержания.
Проверка: 14 колод перерисованы до и после — изменились только Education и Tech (у ЛЦТ модель
декора не нашла, у WorkSpace свой в макетах, у CIP, Luxury, McKinsey, A Year — только фото).
