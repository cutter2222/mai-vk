# Архитектура

Сервис принимает шаблон презентации и материалы, а отдаёт три готовых варианта колоды в
PPTX, PDF и HTML вместе с отчётом аудита. Всё, что он собирает, собрано из объектов
загруженного шаблона: его макетов, композиций, шрифтов, палитры и пиктограмм.

Документ описывает границы слоёв, контракты между ними, граф заданий и поток данных.
Реестр проверок аудита — в [AUDIT.md](AUDIT.md), модели и роли — в [MODELS.md](MODELS.md).

## Из чего состоит

| Сервис | Что делает |
| --- | --- |
| `caddy` | единственный вход: статика интерфейса и `/api/*` в API |
| `frontend` | Next.js 16, статический экспорт; рабочий режим ходит в `/api` того же origin |
| `api` | FastAPI: проекты, файлы, шаблоны, содержание, задания, отчёты, правки |
| `worker-analysis` | очереди `analysis` и `repair` |
| `worker-generation` | очереди `interactive` и `generation` (в этом порядке приоритета), по умолчанию 3 реплики |
| `asr` | распознавание речи для голосового ввода в чате: GigaAM в ONNX Runtime, веса — том `asr_models` (`/app/models`, на сервере `$SERVER_DIR/models`, `make asr-model`); наружу не виден, фразы пересылает API |
| `valkey` | очередь RQ, лимитер вызовов модели, кэш ответов |

Состояние — SQLite в режиме WAL в общем каталоге данных (`pipeline/state.py`): проекты,
файлы, шаблоны, пакеты, задания, варианты, ревизии. Загруженные файлы адресуются по
`sha256`, артефакты ревизий — манифестом (`pipeline/files.py`, `pipeline/artifacts.py`), так
что второй бэкенд хранилища добавляется без изменения слоёв.

## Пять слоёв и что между ними

Границы слоёв — это документы контрактов, а не вызовы функций. Каждый слой принимает и
отдаёт JSON, проверяемый по схеме, поэтому его можно запустить отдельно из CLI и подменить
заглушкой.

```
PPTX шаблона ──▶ parsing.template ──▶ TemplateProfile ─┐
                                                       ├─▶ generation ──▶ StoryPlan, SlidePlan × 3
материалы ─────▶ parsing.content ───▶ ContentPackage ──┘                        │
                                                                                ▼
                                          ComposedDeck ◀── layout ◀── SlidePlan + исходный PPTX
                                                │
                                   ┌────────────┴────────────┐
                                   ▼                         ▼
                              export (PDF,               audit (реестр проверок)
                              миниатюры, HTML)                │
                                   └────────────┬────────────┘
                                                ▼
                                          AuditReport, ревизия
```

| Слой | Каталог | Вход → выход |
| --- | --- | --- |
| Парсинг шаблона | `parsing/template/` | PPTX → `TemplateProfile`: макеты, композиции-паттерны с ролями и слотами, дизайн-токены, постоянные элементы, пиктограммы |
| Парсинг содержания | `parsing/content/` | docx, xlsx, csv, pdf, md, txt, картинки, бриф → `ContentPackage`: блоки, факты с ссылкой на фрагмент источника, наборы данных, ресурсы |
| Генерация | `generation/` | `ContentPackage` + `TemplateProfile` → `StoryPlan` (общий смысл) и три `SlidePlan` (compact, balanced, detailed) |
| Вёрстка | `layout/` | `SlidePlan` + исходный PPTX → PPTX и `ComposedDeck` (что и где стоит на каждом слайде) |
| Экспорт | `export/` | PPTX → PDF (ONLYOFFICE), миниатюры (PDFium), автономный HTML из объектов, а не снимков |
| Аудит | `audit/` | `ComposedDeck`, PPTX, миниатюры → `AuditReport`: 36 проверок, находки, покрытие |

**Что не является слоем конвейера**, хотя живёт рядом:

* `design/` — подгонка композиции под объём содержания: меняет паттерн, дозапрашивает текст,
  режет дубликаты. Работает между планом и вёрсткой по фактам измерений.
* `library/` — собственные композиции в дизайн-системе загруженного файла на случай, когда
  в нём не хватает подходящих страниц. Паттерны самого файла всегда идут первыми.
* `llm/` — единственная точка вызова моделей: роли, кэш, лимитер, повторы, учёт токенов.
  Слои не знают адресов провайдера и не импортируют SDK.
* `pipeline/` — оркестрация: состояние, очереди, артефакты, ревизии, сборка мусора.
* `api/`, `cli/` — способы позвать конвейер. Чат в интерфейсе — способ ввода, а не слой:
  каждое требование ТЗ закрывается явным `GenerationRequest`.
* `contracts/`, `shared/` — модели документов и общие утилиты (настройки, метрики шрифтов).

## Контракты

`contracts/schemas/*.json` — источник истины. Из них генерируются модели Pydantic
(`scripts/gen_contracts.py` → `contracts/models.py`) и типы TypeScript для интерфейса
(`frontend/scripts/gen-types.mjs`). Правило простое: документ, пересекающий границу слоя,
проверяется по схеме, а связи внутри документа — правилами `contracts/validators.py`
(ссылки на слайды, соответствие ревизий, причина у непроверенной проверки).

Версия контрактов входит в ключи кэшей. Смена схемы профиля поднимает `CONTRACTS_VERSION`,
и шаблоны из библиотеки переразбираются при следующем обращении — иначе кэш отдал бы разбор
в старой форме и генерация упала бы на валидации.

## Задания и очереди

Виды заданий: `template_analysis`, `content_import`, `generation`, `repair`, `slide_edit`.
Этапы задания: `queued`, `analyze`, `import`, `story`, `plan`, `compose`, `export`, `audit`,
`repair`, `finalize`, `done`. Состояние задания живёт в SQLite, а не в RQ: пропажа записи
очереди не означает пропажи результата.

Граф генерации (`pipeline/jobs.py: enqueue_generation`):

```
        ┌── template_analysis ──┐
        │                       ├──▶ variant compact  ─┐
content_import ──▶ story ───────┼──▶ variant balanced ─┼──▶ finalize
                                └──▶ variant detailed ─┘
```

Каждое задание варианта внутри себя проходит `plan → compose → export → audit` и публикует
ревизию: файлы становятся доступны раньше, чем закончится всё задание, поэтому первый
готовый вариант можно смотреть, пока считаются остальные. У каждого этапа свой тайм-аут
(`config/app.yaml: timeouts`), у задания — общий бюджет.

Правка слайда (`slide_edit`) и исправление находок (`repair`) идут тем же путём:
`план базовой ревизии + изменения → compose → export → audit → новая ревизия`. Исходная
ревизия остаётся доступной, а устаревшая база даёт `409 revision_stale`.

Очереди: `analysis` и `repair` слушает `worker-analysis`, `interactive` и `generation` —
воркеры генерации; порядок очередей в `--queues` — приоритет, поэтому освободившийся воркер
сначала берёт `interactive`. Туда идёт только фон уже открытой презентации: подписи и
диаграммы-картинки, рендер, итог задания и — если проверка моделью не заказана — смысловой
план по профилю и сборка «как есть» (без модели, около 8 с на 55 слайдов).

Готовая презентация («Открыть как презентацию», вариант `original`) показывается раньше
графа: `submit_generation` сам публикует копию файла ревизией r1, без очереди и модели.

```
POST /api/generations ─▶ r1 (копия файла, ready_at)
        interactive:  подписи и диаграммы-картинки ─▶ r2, если что-то изменилось; рендер
template_analysis ─┐
content_import ────┴──▶ story ──▶ variant original (в последнюю ревизию) ──▶ finalize
                        (interactive без контекстного аудита, иначе generation)
```

Правка из чата, пока у последней ревизии нет плана, принимается и ждёт этих задач
(`depends_on`); база переносится на последнюю ревизию перед запуском.

## Поток данных одной генерации

1. **Файлы.** Интерфейс кладёт файлы в проект (`POST /api/projects/{id}/files`) — один раз,
   дальше по `file_id`. PPTX уточняется вопросом «шаблон или материал».
2. **Шаблон.** `POST /api/templates` ставит разбор в очередь `analysis`. Профиль кэшируется
   по `sha256` файла и версии анализатора.
3. **Содержание.** `POST /api/content` собирает `ContentPackage`: текст разбирается на
   блоки, числа — на факты с ссылкой на исходный фрагмент, таблицы — на наборы данных.
4. **Бриф.** Текст из чата уходит в `POST /api/brief`: модель достаёт назначение, аудиторию,
   цель и ограничения; чего модель не нашла, остаётся незаполненным, а не выдумывается.
5. **Задание.** `POST /api/generations` с `template_id`, `package_id` и настройками.
6. **Смысл.** `StoryPlan`: тезисы, обязательные факты, допущения, покрытие.
7. **Варианты.** Для каждого варианта код подбирает композиции шаблона под тезисы, модель
   пишет текст в слоты, код измеряет вместимость по метрикам шрифта и правит план.
8. **Вёрстка.** Образец-слайд клонируется со всеми связями, слоты заполняются по
   `element_ref`, диаграммы становятся нативными, лишние объекты удаляются.
9. **Экспорт.** PDF, миниатюры, автономный HTML.
10. **Аудит.** Детерминированные проверки по файлу и, если включена, контекстная часть
    моделью по картинкам слайдов. Отчёт кладётся рядом с колодой.
11. **Результат.** `GenerationResult` со списком вариантов, артефактами, метриками, версиями
    скиллов и промптов, режимом исполнения каждого слоя.

## Модели

Все вызовы идут через `llm/client.py`: роль (`llm`, `vlm`) → провайдер и модель из
`config/models.yaml`; кэш ответов, объединение одинаковых запросов, аренда лимитера
(одновременность, RPM, TPM — общий для всех воркеров через Valkey), повторы на 429, сеть,
5xx и негодный ответ, учёт токенов. Промпты лежат в `skills/<name>/prompts/` с версией в
имени файла; версия скилла и промпта входит в ключ кэша и в результат — по колоде видно,
каким промптом она получена. Подробности — в [MODELS.md](MODELS.md).

## Интерфейс

Next.js 16 со статическим экспортом, Mantine 9. Два режима сборки: `real` — запросы в `/api`
того же origin, `mock` — заглушки в браузере (демо и e2e без backend). Экран проекта: слева
чат и файлы, справа предпросмотр — лента миниатюр, крупный слайд с рамками находок аудита,
сравнение вариантов, переключение ревизий. Правка слайда возможна прямо на холсте: выбор
объекта по буквам, боковая панель свойств, добавление и удаление надписи, отмена шагов,
снятие знака шаблона. Ручные правки уходят в `POST …/patches` документом `slide_patch` и
собирают новую ревизию без модели.

## Развёртывание

`docker/compose.yaml` плюс `compose.dev.yaml` для разработки (монтирует `src`, поэтому код
меняется без пересборки образа). Выкладка — `deploy/deploy.sh` (тег выпуска, миграция,
проверка готовности), откат — `make rollback`, резервные копии — `make backup`.
Переменные окружения: адрес и ключ провайдера, адрес Valkey, порты, публичный адрес.
